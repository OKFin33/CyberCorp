# 验证状态

不同类型的证据不能互相替代。安装与结构检查、原生工具读写、独立 Agent 消费、真实接续、多实例协作、业务价值是六件不同的事；**没有证据的部分在这里保持"无"，不因为相邻能力通过而推定通过。**

## 有证据

| 能力 | 证据类型 | 位置 |
|---|---|---|
| 确定性安装、重装保护项目编辑 | 自动化测试（123 项根 unittest） | `tests/test_creation.py` |
| 本地结构检查发现悬空引用、缺失路由、无效 helper | 自动化测试 | `tests/test_verification.py` |
| 原生对象读取的协议行为（离线回放） | 自动化测试 | `tests/protocols/` |
| 启动器的显式命令与 fake-CLI 启动／恢复 | 自动化测试 | `skills/corpo-launcher/scripts/tests/` |
| 独立实例从项目入口开始并交付实际结果 | 合成消费；报告与固定提交号 | [issue-3](evidence/issue-3/README.md)、[issue-5](evidence/issue-5/README.md) |
| 换实例接续：新实例采纳 Owner 答复、更新事实与受影响 pin | 合成消费 | [issue-3](evidence/issue-3/README.md) |

## 无证据

| 尚未验证 | 为什么合成测试不能代替 |
|---|---|
| 不知创建历史的真实接续 | 合成消费者由评估者构造，其起点与真实陌生实例不同 |
| 多实例与跨机行为 | 现有交错证据来自本机离线 API，不证明真实 GitHub 的竞争与原子性 |
| 各 CLI runtime 的真实调用 | 现有证据用 fake-CLI；Kiro 是唯一有适配示例的 runtime，且未做真实账号与模型端到端 |
| 长期推进效果 | 需要真实项目持续运行才能取证 |
| Owner 的实际理解 | 沟通草稿不证明对方读懂了 |
| 在另一个真实项目上完成创建并交给独立实例开工 | 这是可分发性的核心判据，尚未在第二个项目上做过 |
| 业务价值 | 与上述任何一项都不同 |

## 建议的取证方向

**把可确定性验证的一层放进 CI。** 现在的合成消费把两件事混在一起做了：环境是否可用（能否 clone、入口能否读到、路由是否可达、bundle 能否重建）是确定性的；实例是否理解并做出有价值的判断是非确定性的。前者进 CI 之后，后者失败时的归因就是确定的——困难一定在理解层面，不在配线层面。前者进 CI 还会捕获腐烂：bundle 与当前代码的兼容性一旦失效会立刻暴露，而现在不会有人发现。

**非确定性的那层用手工触发的 workflow。** 公开仓库的 fork PR 拿不到 secrets，非确定性输出也会让必跑的检查变得不稳定。手工触发一次真实消费、把报告作为 artifact 上传，验证就有了平台记录——那也是这类证据的常规归处，届时不再需要把产物存进 Git。
