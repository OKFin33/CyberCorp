# 0003 · 切断外部代码继承链，helper 全部改为原创

- 日期：2026-09-13
- 状态：已采纳并验证
- 影响面：`.agents/corp/`、分发模板中的对应副本、`tests/protocols/`、`NOTICE`（已删除）

## 决策

移除四个继承自外部仓库的文件，其中两个的功能由从零编写的实现替代，两个直接废止：

| 文件 | 处置 | 说明 |
|---|---|---|
| `spec-checkpoint.py` | **clean-room 重写** | 108 行 → 176 行 |
| `repo-context.py` | **clean-room 重写** | 447 行 → 313 行 |
| `work-state.py` | **删除** | 旧机制的"评论即状态机"实现，新机制不用 |
| `format-event.py` | **删除** | 同上，事件格式化 |
| `tests/protocols/` | **从零重写** | 旧测试同属继承范围 |
| `NOTICE` | **删除** | 出处声明的对象已不存在 |

`.agents/corp/` 现在只剩四个 Python 文件：`check.py`、`enter.py` 与上述两个重写件，全部为本项目原创。

## 为什么必须这样做

[实测] 2026-09-12 的一次来源核查确认了三件事：

- 那句 `NOTICE` 声明所指的 "earlier maintainer-owned pilot" 是一个具体的外部仓库，其内容明确讨论公司的产研方案与市场需求，并载有"公司正式评审待进行"的决策记录。
- `spec-checkpoint.py` 与来源仓库的对应文件**字节完全相同**；`work-state.py` 相差一处可选校验；`repo-context.py` 保留原主体。所以 `NOTICE` 里的 "adapted"（改编）一词不准确，其中至少一个是直接复制。
- 该来源的著作权归属**未被任何证据确立**。放在个人账号下的仓库、README 中"个人开发基线"的描述，都不能确立版权归属。

许可证决定的是"授予他人什么权利"，无法弥补"是否有权授予"。在权属未确立的情况下以 MIT 公开这些文件，等于授出一份可能并不持有的权利，且**发布后不可撤回**——即使删除仓库，已被 fork、clone 或存档的副本仍然存在。

**选择重写而不是等待权属确认**，理由是成本对比：这些 helper 的功能高度通用（对一段文本归一化后取 SHA-256、把一次 GitHub 观察读成紧凑 JSON），从零实现的代价是可数小时的工作；而权属确认涉及雇佣关系条款解释，周期不可控且结论可能为否。重写让问题消失，而不是解决它。

## 为什么删掉的那两个本来就该删

[推导] `work-state.py`（"replay append-only Issue execution comments"）与 `format-event.py` 是**旧的"评论即状态机"机制的实现**：往 Issue 评论里写结构化事件，再重放出占用与检查点状态。

[决策记录 0001 决策 4] 本轮重构已经把这套机制换成 GitHub 自己维护的 `assignee` 与 `updated_at`，理由是一次字段笔误曾使整条执行记录不可重放——自建记录格式引入了它自己的故障模式。因此这两个文件在新机制下不承担任何职责。**删除它们不是为规避权属而做的妥协，是 0001 本该跟着做的清理。**

## 隔离条件（决定重写是否算独立创作）

重写由一个**独立实例**执行，其输入只有一份从 `docs/corp/mechanics.md` 的规则推导出的功能规格，加上必须保持的接口契约。被明确禁止的行为：

- 以任何方式查看旧实现，包括 `git show`、`git log -p`、`git diff`、`git stash`、reflog 等历史命令；
- 查找或读取来源仓库；
- 取回已删除的 `tests/protocols/` 作参考。

执行者在报告中声明未触碰上述任何来源，并主动列出了六处"规格未写清、由它自行决策"的地方及其依据——那些依据全部来自本项目自有的既有测试（`tests/test_creation.py`、`tests/test_scenario_environment.py`、`tests/scenarios/`），不在继承范围内。

结果上，两个文件的行数与结构均与原件不同（176 对 108、313 对 447）。**但独立创作的判据是过程隔离，不是结果差异**；上述禁令与声明是本次能取得的最强证据。

## 必须保持的接口契约（不属于表达，属于兼容性约定）

重写不能自由改动以下几点，否则 GitHub 上已发布的 Issue 会失效：

- Spec 区域标记为 `<!-- spec:start -->` 与 `<!-- spec:end -->`，各须恰好出现一次且独占整行。
- 归一化规则：CRLF 与 CR 转 LF、去每行行尾空格与制表符、删末尾空行、非空时补一个结尾换行。任何偏差都会改变哈希值，使已发布的 acceptance 行对不上。
- `--checkpoint` 输出格式为 `SPEC_ACCEPTED issue=<n> spec_sha256=<hash> source=<url>`。
- 退出码：正常 0、`--check` 不匹配 1、错误 2。
- `parse_map` 的窄格式契约与 `status` 取值集合。

[实测] 重写后实际验证：CRLF 输入与 LF 输入、带行尾空格与不带，产生完全相同的哈希。

## 验证

- `python3 .agents/corp/check.py --base HEAD` → `status: passed`，`python_helpers` 由 6 降至 4。
- `python3 -m unittest discover -s tests` → **135 项全部通过**（重构前基线 123 项；新写 72 项协议测试，移除依赖已删 `format-event.py` 的一组测试）。
- 本体与分发模板的两个新文件逐字节一致。
- 全仓无残留引用 `work-state` 或 `format-event`，唯一例外是 `.agents/corp/install.json`。

## `install.json` 为何不动

它记录的是本仓库**首次自我安装**时的文件清单与哈希，其中包含现已删除的四个文件。按其自身定义（"records initial provenance, not later adoption"），它是历史事实而非当前状态，因此保持原样。检查器不校验它的内容，不会因此失败。

## 剩余风险

本决策消除的是**代码**的继承链。本项目的方法论、机制设计与文档均为原创表达，即使其思想来源于此前项目的开发实践——著作权保护表达，不保护思想，用一个项目的经验做另一个项目不构成侵权。

仍需注意的是：来源仓库本身若为公开状态，其风险与本仓库无关但独立存在，应单独核查。
