# 0005 · 让声明与事实相符

- 日期：2026-09-13
- 状态：已采纳并验证
- 影响面：`docs/corp/`、`.agents/skills/`、`.agents/corp/repo-context.py`、`CONTRIBUTING.md`、根 `README.md`、`tests/test_template_sync.py`（新增）、分发模板中的对应副本
- 事项：[#9](https://github.com/OKFin33/CyberCorp/issues/9)；系统性部分由 [#10](https://github.com/OKFin33/CyberCorp/issues/10) 持有

## 共同主题

四处改动来源不同，毛病相同：**某处声明的比它实际做到的多。**

| 声明 | 实际 |
|---|---|
| `S7` 一节声称消除"这个工作是否已死"的猜测 | 项目未声明阈值时，猜测一字未减（[0004](0004-fixes-from-first-real-adoption.md)） |
| `verified` 字段名 | 只等于路由表写了 `active`，从不读 target（0004） |
| `atomic_snapshot` 字段名 | 只等于"没有翻页"，而报告由七八次顺序读取拼装 |
| 占用可见（载体 `assignee`） | 账号级字段无法区分同账号的另一实例或自己的上一次运行 |
| 「模板与本体逐字一致」 | 仅靠人工 `cmp` 维持，本次换代中实际已漂移 |

## 决策一：去掉 S1–S8 代号

代号产生于设计阶段的子问题编号，记录的是作者的推导顺序。读者见到 `S7` 必须跳转才知道所指；而八条规则的标题本来就是完整的人话（"Abandoned occupation is discoverable and releasable"），代号只是挡在前面的一层。

小标题、概览表、交叉引用、三份方法文件与贡献指引中的引用形式全部改为规则名。**多数引用直接删除**——`2. **Check it carries its own acceptance** (S1)` 里那个编号没有增加任何信息。已发布的决策记录保留原有代号，它们是历史。

**这件事本该在换代时就做。** 它在换代过程中被识别过，然后随实例换代丢失，最后靠 Owner 的记忆找回；期间贡献指引还把"标它服务的子问题编号"写成了对后来贡献者的要求，反向固化了它。

丢失的原因是机制缺口：CorpMech 有位置放**要做的工作**（Issue-as-Spec）与**已定的事实**（Canon），没有位置放"已经看出来该改、但这轮不做"的东西。GitHub 原生的 Issue 就是那个位置，当时建一个一句话的 Issue 即可，没有建。**产品的第一性原理是不依赖任何单个参与者的可靠性，而这次它依赖了 Owner 的记忆。**

## 决策二：占用改为自我指派加实例标识

`assignee` 与 `requested_reviewers` 都是账号级的。占用一节自己声明要解决的场景就包括"一个实例和它重启后的后继者取同一份工作"——那两者账号完全相同，字段从来分不出。分不出只有两种错法：当成他人在做而绕开本该接手的工作，或当成自己的残留而与另一实例同时写。

审查路径此前已要求"在 PR 上评论一条 runtime 内唯一的 instance ID"，因为审查者字段同样是账号级的。**同一根因，两条路径处置不一致**：一条解决了，另一条没有。现在占用统一为"自我指派 + 带 instance ID 的评论"，并要求在占用前先读已有的占用评论。这不是新增机制，是把已有做法扩展到缺它的那一半，同时把审查路径里对该规则的复述删掉，避免第二个定义处。

该缺陷由首次真实采纳发现：下游项目撞到后**自行**补了承接评论。上游缺的东西被消费方各自打补丁，正是本产品要消灭的现象。

## 决策三：模板一致性交给机器

本仓库是自己的第一个 Corp，`.agents/` 与 `docs/corp/` 既是产品又是自用副本，两者必须逐字一致。此前这条不变量只靠每次手工 `cmp` 维持——而本次换代中它实际已经漂移：`repo-context.py` 的模板版缺少 `InconsistentObservation`，因为第一轮改完同步过、第二轮修测试失败时补的类没有再同步。

新增 `tests/test_template_sync.py`。它同时纠正了一处错误记忆：两个例外文件的差异性质本以为都来自占位符，实际只有入口是（安装器替换 `{{PROJECT_REF}}` 等三个 token），Owner 卡则是**项目自有**——模板版是"如何写你自己的卡"的起点指引，本体版是本项目实际使用的卡。两类例外因此按不同判据检查：入口断言 token 只出现在模板侧，Owner 卡断言两侧都存在且小节结构相同。

该测试上线后立即抓到两件事：上述漂移，以及本次施工中一次 `git checkout <file>` 误还原造成的自伤——工作区改动尚未提交，还原的目标是不含本轮改动的 HEAD。

## 浮现出的判据

**留白本身不是缺陷，留白没有默认行为才是。**

两条规则都留白：`irreversible actions` 一节不规定哪些情况需要 Owner 决定（"让它在使用中形成"），`abandoned occupation` 一节原先不规定阈值。前者有默认行为兜底——统领规则写明"清单之外的动作不需要 Owner 批准"，所以留白处仍有可执行答案；后者没有，执行者不知道该等还是该接管。

这条已写入 `CONTRIBUTING.md` 的准入判据。

## 未决

**自我声明没有任何东西检验它。** 每节的"消除了哪个猜测"、每个字段的名字，都是声明。本次三处缺陷全部属于这一类，而它们能在仓库里躺到真实消费才暴露，是因为没有任何测试、检查或评审步骤会去问"这个声明成立吗"。

检验方法尚未确定，由 [#10](https://github.com/OKFin33/CyberCorp/issues/10) 持有。本次发现三处缺陷的实际方法是逐条设想"最不利的合法状态"——项目什么都没声明、账号共用、上一实例无声消失。这个方法有效但依赖人的判断，不宜做成 CI 硬门禁：硬门禁会教人写空壳来通过。
