# 0006 · 恢复被误删的实例标识与仲裁规则

- 日期：2026-09-13
- 状态：已采纳并验证
- 影响面：`docs/corp/mechanics.md` 的占用一节、`docs/corp/README.md` 的开工必读第一条、分发模板中的对应副本
- 修正对象：[0001](0001-mechanism-layer-rewrite.md) 的一处判断，以及本日早前一次错误的重新设计

## 背景

换代时删除了 `docs/corp/claim-protocol.md` 与 `.agents/corp/work-state.py`，理由记在 0001：认领与释放改用 GitHub 维护的字段，移除自建的 lease／renewal 记录格式——**一次字段笔误曾使整条执行记录不可重放**。

那个理由成立，但**它只支持删掉自维护的事件流**。同一份文档里还有两条不依赖事件流的规则，被一并删掉了：

| 旧规则 | 是否依赖被删的 lease／事件流 |
|---|---|
| 每次执行一个 runtime 内唯一的 instance ID，附生成命令 | 否 |
| 服务器顺序中第一个有效占用者胜出，败者停止冲突写入 | 否 |
| `lease_until` 与 `renew` 事件 | 是 |
| `claim`／`renew`／`checkpoint`／`release` 事件状态机与离线重放器 | 是 |

前两条只需要"评论"这一个载体，而评论在新机制里仍然存在。它们跟着被删是判断失误，不是取舍。

后果在首次真实采纳中显现：下游 Corpo 撞到同账号多实例无法区分，**自行**补了承接评论——上游本来有这个设计，被删掉了，于是消费方重新发明它。

## 今日早前那次重新设计是错的

发现该缺口后，本日早前重新引入 instance ID 时给出的构造方式是"从执行现场派生——runtime 加上占用的分支或工作树——使重启后的实例能认出自己的占用"。

这个方向错了。旧设计写的是 **"A new instance gets a new ID"**，而它更正确：

- 重启后的实例**不是**同一个实例，它没有前任的上下文。
- 让它把既有占用识别为"自己的"，会诱导它直接续做一个半成品而跳过状态核对——而它并不知道前任做到了哪一步。
- 正确行为是把任何既有占用（包括同一现场留下的）都当作需要核对的既有占用，走接管路径：读最后状态与未关闭的 PR、记录观察、然后接管。

Owner 于 2026-09-13 从记忆中指出旧机制"似乎有一套设计"，据此从 Git 历史核出原文。

## 决策

恢复两条，并保持不恢复另两条：

- **恢复**：每次执行一个新 ID，附 `uuid4` 生成命令；上下文压缩只在仍持有占用的同一次执行内保留该 ID；**ID 只标识，不授权**（旧文原话：conveys no authentication or rank）。
- **恢复**：发布占用后重读完整评论，确认服务器顺序中第一个有效占用是自己的；评论不是原子锁，服务器顺序仲裁，败者停止冲突写入而不是协商。
- **不恢复** `lease_until` 与 `renew`：接管条件已改为记录式观察（[0004](0004-fixes-from-first-real-adoption.md)），不再需要租期，且租期正是笔误的来源。
- **不恢复**事件状态机与离线重放器：0001 的删除理由对它们仍然成立。

三条新的故障形态随之写入：发布后不重读就开工；把 instance ID 当作权限；以及既有的账号级误判。

## 判据

**清理一个机制时，逐条问这一条是否依赖被删的载体。** 依赖的随载体走，不依赖的必须单独重新裁定——否则删掉的是一份文档，而不是一个决定。

本次两条被误删的规则都只依赖"评论"，而评论从未被删除。

## 后续检验

这套设计仍有一处未经真实验证：**并发占用的仲裁**。服务器顺序仲裁在合成消费中跑过有界交错，但那是本机离线 API，不证明真实 GitHub 上两个实例同时发布占用时的顺序与可见性。该缺口已在[验证状态](../verification-status.md)中登记为"多实例与跨机行为"。
