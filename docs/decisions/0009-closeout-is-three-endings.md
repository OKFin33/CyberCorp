# 0009 · 收尾是三个结束，不是一个

- 日期：2026-09-13
- 状态：已采纳；本地检查与合成消费通过，真实采纳未验证
- 影响面：`docs/corp/mechanics.md`（新增一节）、`docs/corp/README.md` 的路由表、三份 SKILL 的收尾步骤、`.agents/corp/enter.py`、`tests/test_closeout.py`、`tests/test_entry_and_events.py`、分发模板中的对应副本
- 来源：[Issue #7](https://github.com/OKFin33/CyberCorp/issues/7) 收缩后的剩余范围（Spec pin `3fe416f9…`）

## 决策一：单独成节，不塞进占用节或完成节

两个更省事的位置都被否决：

- **塞进「占用与接管」**：那一节回答"我能不能动手"，收尾回答"这个对象能不能没"。它已是全文最厚的一节（4886 字符），再加一层会把两个不同时刻的判断混在一起。
- **塞进「完成以非自证的证据为准」**：**这正是要区分的东西。** 本节存在的理由就是"结果完成不等于本地现场可回收"；把它折回完成节，等于用一节同时表达"完成"和"完成不代表什么"。

新节按准入判据成立：子问题是"执行结束后留下的分支、worktree、临时 checkout 无人能分类"；消除的猜测是"这个对象能不能没，我的 release 到底证明了什么"。节序放在完成之后、Owner 边界之前——一次执行就是在那个位置遇到它。

## 决策二：三种结束用表格表达，且第三列是"它不证明什么"

Spec 要求三种结束条件"可分辨"。只写一段散文说它们不同，读者仍要自己推导差别。表格的三列分别是结束、它的证据、**它不证明什么**——第三列才是可分辨性的操作形式：

| 结束 | 常见误读 |
|---|---|
| 结果 | 合并了 ⇒ 本地可以清 |
| 占用 | release 了 ⇒ 进程停了 / 候选可删 |
| 现场 | 目录删了 ⇒ 现场结束了 |

## 决策三：判据以原生 Git 反例固定，不靠散文自证

Spec 列了四条不得简化的判据（`clean` 不覆盖 ignored；release 不证明进程停止；closed／曾 merge／删除成功都不证明当前 tip 可丢；squash／rebase 后须核对实际成果）。这些是对 Git 实际行为的断言，因此写成可离线复现的检查（`tests/test_closeout.py`，4 项）：

- `clean -fd` 保留 ignored 内容，`-fdx` 才删掉项目故意不跟踪的本地数据——两种结果都不是"现场空了"。
- merge 之后源分支又提交，tip 不再被包含（`merge-base --is-ancestor` 返回 1，`branch --merged` 不再列出它）。
- squash 之后内容相同而祖先关系不存在（`git diff` 为空、`--is-ancestor` 为 1、`branch -d` 拒绝）。
- `push --delete` 返回 0，ref 消失而对象仍在远端库中——**退出码描述命令，读回描述状态。**

**被否决：断言机制层里有那几句话。** 这类"散文检查"用一个空壳就能通过，恰是本产品批评的形态（[Issue #10](https://github.com/OKFin33/CyberCorp/issues/10)）。**被否决：把清理做成 CI 门禁。** 硬门禁会教人写空壳；而且判断哪个对象独有内容仍在，需要执行者读当前状态。

## 决策四：`enter.py` 修正它声明的东西，不扩张 CLI

Spec 要求先修正调用语义、无真实必要不扩张 CLI。实测该工具创建的是**同一克隆的附加 worktree**（`.git` 是指回原库的一行文件），而它的 `ceiling` 写着"original checkout is not updated"——原工作树、索引、未跟踪内容确实没动，但原库多出取得的提交和一个新分支引用，且该现场的结束必须回到原库执行 `git worktree remove`。**声明的比它实际做到的少一半，方向仍是失真**（同[决策记录 0005](0005-claims-match-facts.md) 的形态）。

改动限于工具说自己是什么：创建后的 `ceiling` 改为准确表述，新增 `continues`（它开的是新分支，不延续任何既有分支或 PR）与 `closeout`（现场注册在原库、`rm -rf` 会留下 prunable 条目、结束现场不等于完成工作或释放占用）；`--dry-run` 不带目标从静默忽略改为报错。

**被否决：加 `--work-branch` 或分支延续模式。** 规则说安全接班优先延续既有分支／PR，但那不需要工具——`git switch` 就够；把隔离工具改成接班工具，是发明没人要的调用语义。**被否决：加 `--close` 之类的收尾子命令。** Spec 明确不引入清理服务；而且工具替执行者做"这个对象能不能没"的判断，正好绕开本节要求的核验与读回。所以工具只负责把话说清，判断留给执行者。

## 决策五：留白带默认行为

哪些现场算可弃由项目声明。项目没声明时的默认行为写在节内：回收本次执行创建、且独有内容已可从共享成果到达的现场，其余保留并写明理由。没有这条默认，"项目未声明"就会让执行者停下来猜——那正是[决策记录 0007](0007-restructure-by-execution-order.md) 定下的判据要防的。

## 合成消费发现的两处，已在同一变更内修掉

三个独立子实例从生成后的项目入口进入（无人向它们交代判据），覆盖完成／接班、临时验证现场、取消／替代与中断四种情形。它们答对了主要判据，并指出两处真实留白：

- **"替代关系记在哪一侧"没说。** 原文只说"record the replacement relation"，消费者只能推断。改为"record on both objects which replaced which"，并把替代信息写进 Native carriers。
- **"交回时 PR 留什么状态"没说，使"优先延续既有分支／PR"这条默认无法执行**——如果前一实例把 PR 关了，后继者没有可延续的对象。补一句：交回的候选保持开启且可发现。

消费者还指出一处**不属于本次范围**的留白：`work-corp` 的"leave a shared checkpoint"没说写在哪里。记在 Issue #7，不在本变更内动。
