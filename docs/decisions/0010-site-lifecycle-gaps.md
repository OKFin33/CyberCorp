# 0010 · 补上现场生命周期的两处缺口，并声明本项目的回收策略

- 日期：2026-09-13
- 状态：已采纳
- 影响面：`docs/corp/mechanics.md`「三种结束」一节、`docs/corp/README.md`、分发模板中的对应副本

## 背景

Owner 于 2026-09-13 指出两个仓库都积累了多条分支，并回忆此前做过一份分支生命周期方法。核查确认：current-volt 的 `docs/agent-work/workspace-lifecycle.md`（8911 字符）正是它，配套测试 `test_workspace_lifecycle_git.py` 在临时仓库与本地 bare remote 上验证 Git 语义。

[实测] 该文件的核心判据已被「三种结束」一节接住——三种结束分离、`clean` 不覆盖 ignored、退出码不描述状态、squash／rebase 须核对实际成果、一台机器的清理声明不代表全部。**那些判据本就来自这份文件**：Issue #7 收缩后的 Spec 是据它写的。

但三块内容没有过来，原因是**收缩 Spec 时我定的剩余范围只到"三种结束可分辨"**，不是换代弄丢的。

## 决策：补两条，不补第三块

**补：收尾责任的划分。** 旧文件写「创建者负责本机现场收尾，实际集成执行者负责共享分支／PR 的收尾」。新版只说收尾属于创建该现场的工作，**漏掉了共享侧归集成者**。

这一漏立刻产生了后果：本仓库七条分支全部已在默认分支而无人回收，而其中四条的集成者是我。按新增的这条，**留下已合并分支的集成者没有完成集成**。

**补：绕过同分支检出限制的禁令。** 旧文件明令不得用 `--force` 或 `--ignore-other-worktrees` 绕过。新版有"优先继续原分支"的方向，没有这条禁令——而绕过它恰好产生占用机制要防的那种冲突写入。

**不补：四步核验的具体命令序列。** 旧文件给了可执行操作：`merge-base --is-ancestor` 判集成、`worktree remove <exact-path>` 而非递归删目录、`branch -d` 被拒不自动改 `-D`、远端用 `--force-with-lease=refs/heads/<b>:<tip>` 做条件删除、`worktree prune --dry-run` 只观察。

这些是操作手册，机制层只放规则与故障形态。**判据留下、动作留在方法文件或项目自有文档**，是本层一贯的分工；把命令序列搬进来会让每个执行者在开工前读一遍它当时并不需要的东西。

## 声明本项目的回收策略

「三种结束」的 `Empirical` 段说：项目把哪些现场视为可回收是经验值，**没有声明策略时**只回收本次执行创建的、唯一内容已可从别处取得的现场。

本仓库此前没有声明，于是落在那个保守默认上——而既有惯例是合并后保留分支（PR #2／#4／#6／#8 皆保留）。**惯例与规则因此冲突，而我两边都是执行者，没有察觉。**

现在入口声明：交付分支在其 tip 成为默认分支祖先后回收，默认分支即恢复来源；移除前对着真实远端核验祖先关系，且只操作精确的 ref。未合入的分支不在策略内——它们可能持有唯一副本。

模板侧写的是要求项目自行声明，并说明不声明的后果，不替项目决定。

## 对 current-volt 的影响

那份 8911 字符文件中属于**项目自有的操作细节与配套测试**不应随 `docs/agent-work/` 目录一并删除。上游只接住通用判据；具体命令序列、该项目的多机现场约定，以及 `test_workspace_lifecycle_git.py` 覆盖的 Git 语义，都是它自己的资产。已在其 Issue #66 记录此项。
