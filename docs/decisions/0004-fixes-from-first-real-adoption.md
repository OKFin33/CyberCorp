# 0004 · 首次真实采纳暴露的两处上游缺陷

- 日期：2026-09-13
- 状态：已采纳并验证
- 影响面：`docs/corp/mechanics.md` S7、`.agents/corp/repo-context.py`、`tests/protocols/test_repo_context.py`、分发模板中的对应副本

## 背景

[实测] 2026-09-13，一个独立实例在另一个真实项目上采纳了 `f8444d2` 的机制层，交付候选并通过该项目的三项 CI。随后一次独立只读审查报告了三个问题，其中一个属于那次迁移本身（远端 Milestone 仍链接旧文件），另两个来自本仓库：**它们是合成消费从未发现的。**

这是本项目第一次由真实消费产生缺陷证据。

## 决策一：S7 的接管条件改为可执行的观察记录

原文的机制段是"对象超过阈值未变化即可接管"，同时在末尾诚实标注"此处不设默认值"。

问题不在缺一个数字，而在 **S7 声称消除的猜测并未被消除**。原文写的是：

> **Guess removed**: whether this work is dead and whether I may take it.

项目未声明阈值时，执行者面对"实例突然消失"仍然只能猜。一条自称消除猜测而实际留下猜测的规则，比没有这条规则更坏——它让执行者以为答案在别处。

改法是换掉判定对象。**"前任是否已死"不可知，"我是否核对了状态并留下记录"可执行。** 接管条件因此改为：读取对象的最后变化时间、未关闭的 PR 与剩余工作，把观察结果记录在对象上，然后自我指派。项目可声明阈值作为跳过该记录的捷径。

这条改动成立的前提是 S7 早已有的另一条规则：**回来的原持有者必须停止其已失效的执行。** 正是这条义务限制了过早接管的代价，使判定不必依赖"证明前任已死"。原文有这条规则，却没有用它来解决阈值问题。

被否决的替代方案：

- **给一个默认阈值（如 24 小时）。** 那是编造的数字。本项目没有观察数据支持任何具体值，写进产品即为伪造经验。
- **要求执行者询问 Owner。** 违反统领规则——举证责任在要求升级的一方，而"实例可能已死"不构成不可逆动作。

## 决策二：`repo-context.py` 的 `verified` 字段改名，并区分两类读取失败

**字段语义作假。** 原实现两处都是 `verified = (status == "active")`，从未读取 target。字段名声称"已验证"，实际只反映路由表里写了 `active`。一个主张"完成声明必须有直接证据"的产品，在自己的观察工具里输出夸大的证据字段。同仓的 `check.py` 反而是诚实的——它把远端目标单独标为 `remote; not contacted`。

改为 `declared_active`，并显式断言输出中不存在 `verified` 键。同时删除 `canon_routes(root)`：它没有任何调用者，且是两处失真实现之一。

**背景对象的失败阻断了主查询。** `observe()` 在读取 Issue 之前先读 focus Milestone，该读取抛出异常后由 `main()` 捕获并退出 2。于是明确指定 `--issue` 时，一个读不到的 Milestone 会让 Issue 根本没被读取。`errors` 字段本就是为这种降级留的，却没有被用上。focus 是背景而非请求对象，其失败改为记入 `errors`。

**但一致性失效不可降级。** 修复的第一版把 `_read_consistent` 的重复读取不一致也一并吞掉了，被既有测试当场抓住。两次读取不一致意味着观察方法本身失效，影响整份报告的可信度，与"某个对象读不到"是不同性质的故障。因此新增 `InconsistentObservation(RepoContextError)`，让它穿透降级路径。

被否决的替代方案：

- **逐条远端核对 target 是否存在，让 `verified` 名副其实。** 每条路由一次额外 API 调用，并引入新的失败模式；而本地路径的解析已由 `check.py` 覆盖。改名解决的是"夸大证据"这个真问题，逐条核对解决的是一个未被观察到的问题。
- **按异常消息文本区分一致性失效。** 脆弱，且把类别判断藏进字符串匹配。

## 后果

- `report["canon"]` 的字段名变化是破坏性的。已采纳 `f8444d2` 的项目需要同步更新；该候选尚未合并，正好在窗口内。
- 测试由 135 项增至 137 项，新增的两项分别覆盖"背景 Milestone 读不到时仍返回请求的 Issue"与"一致性失效仍然中止观察"。
- 本记录是第一份来自真实消费的缺陷证据。合成消费跑过两轮完整场景，两个缺陷都没暴露——`verified` 的取值在合成场景里恰好总是正确，而合成场景从不构造读不到的 Milestone。**这说明合成消费的覆盖边界，而不只是它的规模不足。**
