# 0007 · 机制层按执行顺序重构

- 日期：2026-09-13
- 状态：已采纳并验证
- 影响面：`docs/corp/mechanics.md`（重写）、`docs/corp/README.md` 的锚点、`.agents/corp/check.py`、`tests/test_verification.py`、分发模板中的对应副本

## 先分清两个对象

首次真实采纳暴露了一批问题，处理它们时必须先分清两件事：**CorpMech 本身**，和**某个项目从旧版换代到新版**。两件都要做，但**在后者中暴露的问题不一定属于前者**。

判据分三类：

| 类别 | 处置 | 本次实例 |
|---|---|---|
| 标准机制缺口 | 进机制层 | 接管条件无默认；同账号多实例无法区分 |
| 实现缺陷 | 修代码，不进机制层 | `verified`／`atomic_snapshot` 命名失真；背景 Milestone 阻断请求的 Issue |
| 迁移特有的历史遗留 | 归该项目，机制层最多加一条防止复发的规则 | 六个 Milestone 链接到即将删除的旧文件 |

第三类最容易误判。为它在机制层加一个检查工具，是**给一个坏做法配探测器**——见下文「远端引用」。

一个反向要求同样重要：**机制层要自洽、一体、干净、薄。** 逐个问题贴补丁会破坏这四项，即使每个补丁单独看都成立。本次重构起因正是察觉到补丁堆叠：同日先引入一个错误的实例标识派生方式，又撤回它。

## 决策一：节序改为执行遇到它们的顺序

原顺序是推导顺序。去掉 `S1`–`S8` 代号后，物理排列仍留着那个顺序——**代号只是推导痕迹的表层，排列是它的底层。**

新顺序按一次执行的时间轴：找到工作 → 占用 → 单元的验收 → 单元的大小 → 完成 → 何时必须问 Owner → 事实在哪。前四条是流程，后两条贯穿全程。

## 决策二：占用与接管合并

它们被分成两节，是因为 clean-room 推导把它们产出为两个子问题。但执行者在**同一时刻**面对它们：看到一个对象，判断能否动手。

分开的代价是可验证的：

- 一处交叉引用作为胶带：占用节末尾写「由下面那条路径接管」。
- 一条规则说了两遍：「新占用不继承旧占用的任何东西」与「不要把既有占用当成自己的」是同一条。
- 两节的 Native carriers 都列 `assignee`。

合并后 4886 字符、9 条故障形态（原为 5418 字符、13 条）。**节数没减少**——腾出的位置给了独立出来的元规则段。

## 决策三：Owner 交互在一处闭合

「何时需要 Owner 决定」与「Owner 的答复怎么进入事实层」原先分在两节。它们是同一次交换的两端。归属信息、适用范围、以及采纳或**明确拒绝并记录理由**的生命周期，现在与发出请求的那条边界规则在一起。

## 决策四：元规则移出为独立段

「改这套规则本身」原先是持久事实节的一部分，理由是规则集也是持久事实之一。逻辑成立，但混淆了层次：**那是关于本文档的机制，不是关于项目工作的机制**，而它让全文最厚的一节更厚。

现在是文末独立段，开头即声明「本节不是子问题之一」。本轮得出的两条判据随之写入该段：留白必须带默认行为；每条「消除了哪个猜测」都要在最不利的合法状态下检验，字段名不得强于它实际计算的东西。

## 决策五：远端引用规范，而非检查工具

六个失效 Milestone 的根因是远端对象直接引用了具体方法文件。曾计划做一个检查工具扫描失效引用（[Issue #11](https://github.com/OKFin33/CyberCorp/issues/11)），**方向是反的**：只要允许这种引用，每次重组都会断一批，工具只能事后报告。

改为一条规则：本目录之外指向规则的任何东西——Milestone 描述、Issue 正文、项目 README、外部文档——都经入口或路由表。两者稳定，它们背后的文件会被重组。`#11` 以 not planned 关闭，不新增代码、不新增 API 往返。

已存在的六个失效链接属于 current-volt 的迁移事项。

## 决策六：结构检查覆盖锚点

`check.py` 原先验证链接的路径存在，不验证锚点。**本次重构改节标题时立刻撞到**：入口的一个锚点失效，而检查仍报 `passed`——路径还在，所以无人报告。

已加校验，并以一条测试固定：链接到真实标题通过，链接到改名后的标题失败。测试从 `mechanics.md` 自身读第一个标题算 slug，不硬编码具体标题。

## 读完全文后否决的一项合并

先前提议把「单元自含验收」与「单元适配实例寿命」合并，理由是执行时连续。**通读后否决**：它们回答不同问题——一个是 Spec 的内容与版本协议，一个是单元大小的判据——各 1600 字符都是合理体量，重复只有一句引用。合并只减少节数，不增加自洽性。

**减少节数不等于变干净。** 合并的判据是执行者在同一时刻面对它们，不是主题相似。

## 后果

- 全文 20619 → 21680 字符。**净增来自新内容**，不是臃肿：远端引用规范、两条元判据、Owner 答复的两条故障形态。合并与压缩省下约 630 字符。
- 故障形态 36 → 35 条。
- 测试 142 → 143 项。
- 节标题变化使旧锚点失效。任何按固定版本引用了 `mechanics.md#…` 的下游项目需要更新；采纳候选未合并者正在窗口内。
