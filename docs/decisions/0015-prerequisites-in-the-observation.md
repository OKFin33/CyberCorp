# 0015 · 未满足的前置条件属于观察结果

## 处境

`work` 的选择规则要求「原生前置已满足」，而全局观察对每条 Issue 只输出占用、标签、状态、更新时间与未合并候选。**规则要求执行者判断的东西，它拿到的数据里不存在。**

在一个真实采纳项目上实测：三个 Issue 各有 3–4 个未关闭的前置，依赖关系在平台侧完全正确，而观察把它们全部报为可取。这不是偶发误差，是给定数据下的必然结果。

读取依赖的函数早已在同一份脚本里，只在单 Issue 模式下被调用。全局模式没有接它。

## 决定

未满足的前置进入全局观察，每条 Issue 一个 `open_prerequisites`，只列仍未关闭的编号。

**列编号而不是计数。** 计数只能告诉执行者"不能取"，不能告诉它在等什么，于是它要么再读一次，要么放弃判断。一个需要额外动作才能用的信号会在某处不被使用——这条判据在本仓库已有两个先例。

**只对确有未满足前置的 Issue 多读一次。** 依赖摘要随列表读取一并返回，所以"有没有"是零成本的；只有"具体是哪些"需要一次请求。绝大多数可取的 Issue 因此不产生任何额外读取。

机制层原有两个可取性信号（未合并候选、Owner 决定标签），现在是三个，并明确三者不可互换。`work` 的规则改为引用观察报告的三项，不再要求执行者自行确认。

## 被否决的替代方案

**让执行者自己去查前置。** 那正是当前状态，而它已经产生了错误判定。规则若要求一个动作，提供数据的一方就该让那个动作不必发生。

**只报一个布尔判定。** 它把"为什么不可取"藏起来，于是执行者无法在报告里说明自己为何跳过某项，接手者也无法核对那个跳过是否仍然成立。

**把可取性算成一个字段，由观察直接给出结论。** 观察的职责是报告状态，不是替代方法文件做判断。三个信号的组合方式可能随方法演化，把它烧进观察工具会让那个演化需要改工具。

**在采纳侧本地打补丁。** 缺陷在上游，而它会在每个采纳者身上重现。

## 影响

新增字段，不改动既有字段。旧 payload 缺少依赖摘要时报告为空列表，与"未声明依赖"同义。

按 Owner 于 2026-09-14 的分批决定，本次只随该修正发版；同批识别的另外三项缺口（规划载体的类别、分支保护与其声明不符、判据与运维记录的归处）等一个自然换代窗口，判据是缺陷是否正在造成错误判定。
