# 0014 · work 的身份是实现者

- 日期：2026-09-14
- 状态：已采纳
- 影响面：`.agents/skills/work/SKILL.md`（重写）、`bounded-planning`、`review`、分发模板

## 背景：一个由激励结构造成的偏向

OSeria 的首次真实消费交付了一份覆盖核对报告——九个缺口，各指向固定源路径。执行合规、验证充分。Owner 由此提出更根本的问题：**若 `work` 带有调查性质，Agent 会普遍偏向查漏补缺而非推进项目**，而大部分 Corpo 应当做的事是实现。

推敲确认这不是措辞问题，是激励扭曲：**查漏的边际成本极低且永远有产出**——总能再找到一个缺口，写成报告看起来充实，而项目没有前进一步。实现相反：可能失败、可能被审出问题、有明确完成点。两者都算 `work` 时，理性的执行者倾向前者。

而 `work` 是最常被触发的一类。另两类由触发条件保护：`review` 只在关闭条件成立时开启，`bounded-planning` 只在无可取单元时触发。**`work` 门槛最低，恰好缺这一层。**

## 决策：约束产出，不约束过程

Owner 的第二条纠正划清边界：**不希望 `work` 的 Agent 无法调研或联网搜索**——过程不该受约束，只有交付必须是推进成果。

因此不采用禁令。**点名"不要做什么"会把它放进视野**，而约束过程还会连带禁掉阅读、搜索与试做，那些正是实现的实际发生方式。

改为把产出定义成说明无法满足的形态：**能跑且检查通过的变更**。一份报告没有检查可以通过，所以它不合格而无需被点名——[实测] 四份方法文件中"调查／查漏"类词汇残留为 0。文件同时正面授权：`How you get there is yours — read the code, search, prototype, throw the first attempt away.`

## 删去无法论证必须存在的解释

Owner 的判据：**除非能论证某个理由必须存在，否则它不存在。**

逐条检验后两句留下：为什么改共享前提要先找它的 owner（否则评审会变成关于你的代码而不是关于那个前提）、为什么前提被证伪要停下（继续会产出建立在它上面的东西）。各一句，各消除一处猜测。

删去的包括一段三句话的范围蔓延论证——**它同时还在约束过程**，两个问题一并解决。

## 自洽性检查：三处逐份看不出来的问题

Owner 要求确认新写的 skills 自洽而非满是补丁。**互相对照而非逐份检查**，发现三处：

**交接没闭合。** `work` 让实现者把范围外的发现记在 Issue 上"因为有界统筹会读"，`intake` 把跨多处的失效交给它，`review` 把缺少的单元交给它——而它的读取清单里没有这三个来源。**三份文件指着一个不读的读者。** 已补，并写明那些是其第 4 步的输入而非额外义务：没被读到的那个就是没人会补的缺口。

**`work` 复述了机制层的规则。** `A PR whose checks pass is completion` 是机制层原话，而机制层开篇即声明其他文件只可引用不可复述。改为指向该节并陈述交付物。

**`review` 既无边界节也无故障清单**，另三份都有——它的约束只活在步骤里，故障形态无处安放。两者补齐。

保留一处不对称并记录理由：`work` 有 `Which Issue` 一节而另三份没有。**它是唯一需要选择对象的一类**，其余的对象由触发状态直接给出。

## 一处施工失误

发版提交时脚本在 CHANGELOG 断言处失败——上一批改动未加"未发布"节，于是版本号与 README 已改而变更记录与本决策记录未写，且该不完整状态已被提交。**发版脚本假定了一个前置状态而没有核对它。** 补齐后重新验证。
