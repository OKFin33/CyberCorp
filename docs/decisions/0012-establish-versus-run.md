# 0012 · 建立与运行分开，运行侧四类工作，入口只答一个问题

- 日期：2026-09-13
- 状态：已采纳
- 影响面：`.agents/skills/`（移出一份、新增一份）、`skills/cybercorp/references/`、`docs/corp/README.md`（重构）、`docs/corp/mechanics.md`、`docs/corp/canon-map.yaml`、`.agents/corp/check.py`、`.agents/corp/repo-context.py`、`tests/`、分发模板

## 起点：两个问题暴露出同一个混淆

Owner 问：**把仓库变成一个可用的 Corp，不是 CyberCorp 这个工具该做的事吗？** 以及 `prepare` 的目的究竟是"仓库刚建好时的一次性动作"还是"每次开工前的准备"。

核查后确认它混了两件事。[实测] 七步里前三步是配置——核实原生工作面并映射进 `canon-map`、精简那份被无条件读取的文件、采纳必要的 Canon；后四步是规划——派生路线、发展近期结果、建立首批工作。**而后四步与 `bounded-planning` 做同一件事**，差别只在输入里还没有现存 Issue。

于是产生一个每次都要付的成本：**每个执行者每次开工都要判断一次"我是不是该先 prepare"，而那个判断 99% 的答案是否。**

## 决策一：分成两个大阶段，Owner 只在前一个必须在场

**建立阶段**（Owner 与 Agent 都在场，一次性）：Phase 1 是安装器——纯确定性地复制文件、替换占位符、生成 `canon-map` 骨架、写溯源。Phase 2 需要判断也需要 Owner，成为分发侧的 `establish.md`。

**运行阶段**：四类工作，`.agents/skills/` 下不再有配置类文件。

这个分法不是分层美学，它落实第一性的一半。Owner 不可靠不等于 Owner 无用——**他的注意力必须花在只有他能给的东西上**。[记录] baseline 第 161 行的原话是"人只给不可推导的输入"。建立时他必须在场，运行时不必，除了授权不可逆动作。

分发侧因此三件齐全：装（`brief.md`）、配（`establish.md`）、换代（`migration.md`）。

## 决策二：新增 `intake`，因为 Canon 的活性主要来自外部

初稿里我把 Canon 更新写成三类工作的副产品——有界统筹写被否决方案、工作写跨模块契约、审查写判据。

**Owner 纠正：那不是他说的新陈代谢。** 主要途径是外部输入——需求变化、Owner 有了新想法、OSeria 从 Pi 换到 Deepseek Harness、海外项目从 Postgres 换到 MySQL。**那些不是任何一类工作干出来的。** 我的写法是"为了让 Canon 变成活的而强行与其他工作建立联系"。

而机制层第 225 行早已有这条规则：Owner 无请求地提供输入，其生命周期终于采纳或**明确拒绝并记录理由**。**规则在，方法文件没有** —— 唯一提到它的是只跑一次的 `prepare`。

**这是同一形状的第二次出现。** 决策记录 0011 记的是 planning 规则在而方法文件缺；这次是 intake。规则有归属、有测试、有检查；顺序没有，所以顺序在重构中蒸发。

`intake` 排在四类之首：**一个已变更的前提会让后面三类全在错的基础上工作**，而在三个 Issue 关闭之后才发现，代价是那三个。

被否决的方案：**"只有人类可以调用"的限制。** 它想防的是 Agent 自造事实，但真正的防线是归属五项（responder、channel、time、applicable scope、available source），而机制已要求，并允许执行者转录、禁止伪造。多加一道限制的代价是 Owner 必须亲自开一个实例才能让新需求进来——那正好违反"不要求创始人一直关心"。

## 决策三：材料不自动进仓库

一份 PRD 五十页，其中不可推导的可能是三句。**Canon 记那三句。** 进入仓库的是提取出的事实加一个可得来源的引用，而那个引用**可以是"无"，但不能省略**——机制的 `available source` 字段正为此存在，我今日转录一份私有会话的检视结论时用过它。

这条规则同时防两件事：**Canon 退化成材料堆**（若材料能整份进来，最省事的做法就是全存进去，而 Canon 的定义随之失效），以及**不该进这个仓库的东西被顺手存进来**。

后者不是假想。[故障] 我今日早晨在一个非公司域目录里留了 447MB 公司项目的会话记录近一日，当初放进去的理由正是"先存着，分拣完再清"——**存进来一步省事，清出去一步靠记忆。**

## 决策四：Canon 维持"少量不可推导内容加路由"，不做成文档仓库

Owner 提出的选择：把 Canon 做成知识仓库，让 Agent 一处拿到全部上下文；或维持现有定义。推敲后维持现有定义，三层理由：

**一、文档仓库最终也需要路由。** 上下文有限、压缩有损——「单元适配实例寿命」整节建立在这个事实上。仓库形态会超出一个窗口，于是"读 Canon"从确定动作变成需要判断的动作，路由并未消除，只是搬进了内部。

**二、复制材料就是制造会过期的第二权威。** 同一判据今日已用过两次：否决"存储 Spec wave 批次"（任一 Issue 移动即过期）、否决"维护优先级 label"（需人持续维护）。搬材料进 Canon 是同一模式第三次出现。

**三、不可推导才需要保存，而这在 Agent-heavy 开发里意味着很少。** [记录] Owner 自己给过这个逻辑（baseline 第 84 行）：代码可被替换修改，故实现代码不应是 Canon。同理适用于文档——需求描述、交互细节、验收场景都能从意图加约束重新生成。**Canon 小不是审美选择，是因为大部分东西真的可以重新生成**，而保存它们花的是每个执行者的注意力。

反例检验：指针不可达时路径 B 会断。但机制已有"已知必需来源不可得时暂停依赖它的决定，无关工作继续"，而这比复制一份更正确——**若 Agent 无权读那份文档，它本就不该是工作前提**；复制只是把"读不到"换成"读到一份可能已错的"。

**因此改进方向是路由的准确度，不是 Canon 的体量。** `canon-map` 每条新增可选的 `answers` 字段，说明它回答什么问题，使执行者不必打开数条来找需要的那条。字段可选，写在它之前的路由表继续有效。

## 决策五：入口只回答一个问题

[实测] 一次真实规划执行为决定做什么读了 `mechanics.md` 全文 25188 字符，然后去列 skill 目录、并查一份已退役的旧 planning skill。它没做错——入口没有状态判定表，推断是唯一路径。

入口重构为三段：**你该做什么**（六行状态表，跑一次 `repo-context.py` 即可判定）→ **开工前**（占用，因为它必须发生在读代码之前，只有入口能保证这个时序）→ **统领规则与本项目的不可逆动作清单**。其余全部移到分隔线之后，标明命中才读。

必读区由 9206 字符降至 3865。**信息一件未丢，只是从"提前读"变为"需要时读"。** 移出必读区的包括：原五条规则摘要中的四条（第 3 条本就是重复统领规则，另三条是机制层摘要，而方法文件每步都指向对应小节）、按场景查规则的路由表（它自己就叫 "for what you are doing"）、取工作副本、外部输入、现场回收策略。

## 决策六：检查点与释放合并为一条评论

[实测] 今日四个实例全部发了两条——一条检查点、一条释放。机制里找不到要求它们分开的规则；来源是旧协议的两个事件类型，而新机制删了状态机却没说可以合并。

它们是同一动作的两面：说清交付了什么、候选在哪、剩什么、什么能恢复它，以及占用已释放。分成两条多一次往返、多一件要读的东西，不多一个事实。

## 决策七：未完成的建立必须可检测

[故障] 刚装完的项目跑 `check.py` 得到 `status: passed`，而 `canon-map` 里 `current-delivery-focus` 与 `active-change-specs` 都是 `unresolved`。**一个只做了一半的 Corp 通过了它自己的检查。**

而 `unverified_routes` 这个字段在正常项目里也有内容（远端目标标为"未联系"），所以看到它有两条不会觉得异常。**Phase 2 是否被执行，此前只靠"恰好没人先建 Issue"。**

现在发一条明确的 note，指名两条未解析的路由、指向 `establish.md`、并说明不要在此派工作 Corpo。**不设为失败**——那会阻塞刚装完的项目做任何事，包括完成 Phase 2 本身。

## 后果

`.agents/skills/` 四份纯工作方法；分发包三件建立与迁移工具；入口一张六行表加两条规则。对下游破坏性：方法文件增删、入口结构变化、`canon-map` 可选新字段。按已立的采纳约定，这些经发版才到达采纳者。
