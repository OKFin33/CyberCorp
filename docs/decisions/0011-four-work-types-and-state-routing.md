# 0011 · 四类工作、去掉后缀、入口按状态路由

- 日期：2026-09-13
- 状态：已采纳
- 影响面：`.agents/skills/`（三份改名、新增一份）、`docs/corp/README.md`、`docs/corp/mechanics.md`、`tests/`、分发模板

## 背景：一个继承下来的缺口

Owner 指出老版本把 Agent 的工作分为三类——**有界统筹、工作、审查**——并问这些定义是否还存在。

核查结果：**规则都在，方法文件缺一份。** 机制层五处提到 planning 作为动作（缺口本身就是工作、先建载体再占用、跨 Issue 生成前先收敛、两条故障形态），但 `.agents/skills/` 只有 `prepare`／`work`／`review`。而 `prepare` 的定位是"装完后建立路线与首批工作"，是**一次性初始化**，不是常态的有界统筹。

[实测] 这个缺口不是重构造成的：换代前 `4e0e030` 的 `.agents/skills/` 同样是这三份，`prepare-corp` 当时的 description 是 `Establish or complete whole-project Corp preparation`。**我重构时照既有构成重写，没有回头核对"三类工作是否各有方法文件"**，还因为把 description 收窄为 "Use right after installation" 而让缺口更明显。

同日我判定下游一份 `to-tickets` skill 被新版取代时，列了五行规则对照表——**核对的全是规则层，而方法文件一半价值在顺序**。如果当时对照的是"三类工作各有方法文件"这个结构，会立刻发现上游少一份。**我对照的是自己的产物，而产物本身缺一份。**

规则有归属、有测试、有检查；顺序没有。这是重构中最容易蒸发的一层。

## 决策一：四份方法文件，去掉 `-corp` 后缀

`prepare`（一次性配置与整体准备）、`bounded-planning`、`work`、`review`。

后缀去掉的理由是它在 `.agents/skills/` 下冗余，而两处都叫 skills 曾造成实际混淆：Owner 查看 `skills/` 时只见分发包两份，误以为方法文件被删。

**破坏性**：已采纳的项目引用旧路径。

## 决策二：入口按可读状态路由，而非按场景描述

[实测] 一次真实规划执行读了 `mechanics.md` **全文 25188 字符**，然后才去列 skill 目录、并去查一份已退役的旧 planning skill。它没做错——**入口没有告诉它"按状态该做哪类工作"，只能自己从规则里推**。

入口首段现在是状态判定表，位于统领规则之前：跑一次 `repo-context.py`，按输出选工作类型。判定条件全部可读，不需要 Agent 判断：

| 状态 | 触发 |
|---|---|
| 当前 Milestone 有未标 Owner 决定的 open Issue | `work` |
| 无可取 Issue 且关闭条件未成立 | `bounded-planning` |
| 关闭条件**成立** | `review`（唯一入口） |
| 无当前 Milestone 或已关闭 | `bounded-planning` |
| 装好但无路线、无可取工作 | `prepare` |

**改成状态判定而非顺序，使 Owner 描述的那个循环自动成立**：审查产生新 Issue → 状态变回"有 open Issue" → 触发工作 → 那些 Issue 关闭 → 状态变回"关闭条件成立" → 再次触发审查。不需要单独规定循环，也不会在中断后失效。

## 决策三：审查不创建工作

审查者不得修改被审对象，而创建 Issue 并改关闭条件是设计动作。因此审查的产出只有发现，按性质分流：阻塞项回到产生它的 Issue；确实缺少的单元交 `bounded-planning`，**由它创建并更新关闭条件**；属于 Owner 的决定交 Owner。

漏掉"更新关闭条件"会造成死循环：旧条件仍可满足，审查在已经变化的阶段上反复开启。

## 决策四：Spec wave 从依赖派生，不存储

原设计有"可从依赖派生 Spec waves 帮助安排并行"，而我此前的评估指出过"wave 的承载物未指定"。**答案在那句话里：不存储，从原生 `blocked_by` 关系算出。** `repo-context.py` 已返回 `relations`，数据在。

存一份批次列表就是第二个权威来源，而它在任一 Issue 移动的瞬间过期。

## 一处被 Owner 当场纠正的错误

有界统筹的初稿把"四个限制"放在步骤之前，并写着"在读步骤前先读它们"。

Owner 的纠正：防止它成为无界决策者固然重要，**但那服务于"做出其他 Corpo 可以依赖的规划"这个推进任务，不能反过来**——而这个坑此前踩过，入口里"推进交付高于改善推进的条件"正是为它加的。

已重写：开头是产出什么与完成判据，步骤在中间，边界移到步骤之后，且每条改为陈述**越界会使产出无法被接手**，而不是"你不许"。第四条原限制"产出必须可被接手"移出限制清单——**它是任务本身，不是约束**。

## 未解决

「优先级最高」仍无可读载体。机制说"取优先级最高的 open Issue"，但 `mechanics.md` 中 `priority` 只出现在那句规则里，`repo-context.py` 也不排序。执行者只能自行推断。这与本次的状态路由是同一类问题——**要求判断处未给可读数据**——但修它需要先定优先级的原生载体，留作独立事项。
