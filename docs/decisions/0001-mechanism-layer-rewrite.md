# 0001 · 机制层重写与仓库结构常规化

- 日期：2026-09-12
- 状态：已采纳，尚未被真实 Corpo 消费验证
- 影响面：`docs/corp/`、三份 skill、分发模板、仓库顶层结构

## 为什么记录这些

机制层从 11 份规则文档收敛为 2 份，硬规定从约 30 条降到开工必读 5 条。[变更记录](../../CHANGELOG.md)说明了改成什么，本文说明**为什么**，以及**哪些替代方案被否决、理由是什么**。

不记录理由的后果是具体的：下一个维护者（包括原维护者本人）会看到 30 条变 8 条，不知道每条是从哪来的，于是把它们加回去。按本项目自己的规则（`docs/corp/mechanics.md` 第 S8 节），决策及其理由、被明确否决的方案及否决理由都属于共享事实层——这份文档就是它在本项目的实例。

标注约定：**[故障]** 表示依据来自实际使用中真实发生的事件；**[推导]** 表示从第一性推出；**[实测]** 表示由本次核查取得的事实。

## 决策

### 1. 机制层按子问题切分，而不是按场景

原来的 11 份文档按场景组织（开始工作、认领执行、跨事项协调、阶段交付、沟通、验证、恢复损坏历史……）。现在按八个子问题组织，场景退化为入口里的一张路由表。

**[实测]** 场景是投影，不是归属。同一条规则会出现在多个场景里，于是必然复制——独立审查的触发条件在 `development-loop.md`、`claim-protocol.md`、`milestone-delivery.md`、`review-corp/SKILL.md` **四处**被分别写出，而吸收规格自己承认这是待统一项（原文要求"实现时同时更新……避免新旧规则并存"）。一份会话里记下的待办，没有在后续会话里被执行。

**被否决：** 保留 11 份文件，只给现有 30 条规定挂上父节点。**否决理由：** 那 30 条的措辞、粒度和组织方式都是在"堵住某个问题"的语境下写成的。挂父节点能修好结构，修不好表达——一条为堵漏而写的规定，读起来仍然像禁令而不像"这里不用猜"。

### 2. 统领规则，且举证责任在想上升的一方

入口顶部只有一条规则：不可逆动作清单之外的动作不需要 Owner 批准。它不是众多规则之一，它决定别的规则有没有资格要求 Owner 介入。

**[故障]** 连续多轮实际使用中，多个实例已经识别出下一步的产品能力工作，却都归类为"可能改变交付承诺，需要 Owner 决定"，转而去做工程基建收尾。当时的诊断原文是"不断完善开工条件，却不真正开工"。而规则里**已经写明**"普通排序不是审批门槛"——授权文字存在，没有转化为行为。

**[故障]** 一次独立复查给出的对比：统筹声明流程有七步细则，而"怎样把产品目标持续变成工作"只有一句抽象原则；复查结论是"怎样合法进入工作，比怎样交付下一项产品能力明确得多"。

**被否决：** 只写否定式授权（"这些动作不需要批准"）。**否决理由：** 问题不是执行者以为需要批准，是它**倾向于把事情归类为需要批准**。否定式授权把归类权留在执行者手上，它可以永远判断"这件事可能改变承诺"。因此改为：要上升，必须指出命中清单的哪一项；指不出就执行。"可能影响""不确定是否""为了安全"不是清单条目。

**由此得到一条一般判据，它同时进入入口**：**推进交付优先于改善推进的条件。** 收紧一个检查、整理基建、补完一份文档、复查一件已完成的事——这些在有交付需要它们时是工作；**指不出它解锁了哪次交付，它就不是下一件该做的事**。

这条判据也用来审视机制本身：**任何让执行者把注意力从推进转向照顾机制的设计，默认可疑。** 每条规则都要能指出它消除了哪一处猜测，指不出就说明它在增加要照顾的东西而不是减少要猜的东西。

**不靠给 S4 补细则来解决。** [实测] 重构后 S3（完成需要外部凭证）2481 字符、6 条故障形态，S4（总有下一件事做）1447 字符、3 条——防虚假声称仍是推进的 1.7 倍。这个不对称不该靠注水填平：虚假声称有几十种形态，每种都要单独堵；而推进的形态很少（取下一件、做完、交付）。真正缺的不是细则，是**两者冲突时按什么判**，那就是上面那条判据。

### 关于记录本身

上面这三条一般判据——推进优先、理由归决策记录、无条件读取的文件只放执行者需要的东西——在形成时都只被用在了当次修改上，没有落盘。它们是 2026-09-13 被逐一追问出来的，而在那之前没有任何机制会发现它们只存在于对话里。

由此得到的判断：**记录故障比记录判据更重要。** 一次真实的翻车不可重现，没记下来就永远没了；而从故障推到判据那一步任何有能力的执行者都能重走。上述三条能被重新推导出来，正是因为 F1、F5、F6 这些故障的记录在。所以投入应优先保证故障落盘——判据漏掉损失有限，前提是它的来源在。

两个落地手段随之产生。S8 多了一条故障形态（"一条在工作中形成、被用于该工作、却从未写下的判据"），让这件事至少可诊断。`check.py` 在机制层变更未触及 `docs/decisions/` 时输出一次提示，且仅在该目录存在时触发。

**提示不设为失败。** 硬失败会让执行者学会写一句空洞的记录去过关，而一份为通过检查而写的记录会给出一个编造的理由——那比没有理由更有害，因为下一个人读它正是为了知道"这里为什么这样"。

### 3. 不设硬规定数量上限，改用三条准入判据

**[推导]** 数量上限本身就是一条没有父节点的规定，会变成新的官僚；而且它会误伤——真的需要第七条时，上限没有依据拒绝它。数量是果，准入是因。

三条判据：**双向可指认**（一条规则必须能同时指出它服务哪个子问题、消除了执行者必须猜测的哪一处，缺一不得进入）、**单一定义处**（每条规则只有一处定义，其余只能引用，新增前检查该子问题下是否已有等价规则）、**必读可见**（入口必须公布完整的开工必读清单且逐条写全文，不设上限，但必须是可见的一整块）。

第三条替代了数量上限：一份长到不像话的必读清单，写的人自己会先觉得不对。

### 4. 认领与释放改用 GitHub 维护的字段

移除自建的 lease／renewal 记录格式，改用 `assignee` 与 `updated_at`。

**[故障]** 一次字段笔误（某字段被写成 null，而校验要求非空）使一条 Issue 的执行记录无法重放。技术决定和正文内容都还在，但"释放"不能算有效，处置方式是保留坏历史、停止该执行、把未完工作转到新 Issue。**自建记录格式引入了它自己的故障模式**，而 `assignee` 和 `updated_at` 由 GitHub 维护，执行者填不错。

**保留：** "旧持有者回归后必须停止已失效的执行"这一条留下了——它是真实故障的解，不是推导出来的。

**保留的自限：** 非原子的读后写声明不能证明排他性。可见占用降低碰撞，不消除碰撞。

### 5. 占用扩展到没有预先载体的动作

**[故障]** 两个实例各自发现"近期工作不足"，都没看见对方，各自开始整理下一批工作规划，最后才发现重复。原有认领机制只能仲裁"已存在的同一个 Issue"，不能仲裁"两个实例各自新建的规划 Issue"——故障发生在**占用对象被创造出来之前**。

**[故障]** 三个实例各自完整审查同一个 PR 约十分钟，事后才发现重复。根因是"审查"这个动作当时没有可占用的载体。

因此规则改为：任何动作开始前必须在原生对象上留下可见占用。Issue 用 `assignee`，审查用 `requested_reviewers`，尚无载体的工作（生成下一批工作、重排优先级）**先创建载体 Issue 再开始**。

### 6. 独立审查是核心机制，不是经验性约束

**[推导]** 完成需要不依赖自述的外部凭证（S3）。凭证分两部分：可自动化的（CI）和不可自动化的（实现是否满足意图）。后者在单个 Issue 粒度上成本超过收益，在 Milestone 粒度上既必要又可行。**所以独立审查是 S3 在 Milestone 粒度的实现，不是额外的质量流程。** 这也解释了为什么它挂在 Milestone 而不是每个 PR——那正是"替换逐 PR 默认审查要求"当初要解决的事。

**同时修正一处稳健性缺口：** 原先"Milestone 是否可以进入收尾阶段"由规划该 Milestone 的实例判断，那是**规划者自评**——它不违反"实施者不能审自己实现的东西"，但规划者同样有立场。现在规划者只在阶段约定里声明**机器可核对的关闭条件**（哪些 Issue 关闭、哪些 PR 合入、哪些检查绿），条件达成即可开审。任何实例判断"阶段是否接近完成"这个动作在新设计里不存在。

### 7. Canon 是路由表加少量内容，都在 Git 里

Canon 直接持有的只有别处放不下的东西：跨模块契约、架构决策及其理由与重新考虑的条件、被明确否决的方案及理由。其余是指针。Canon 不含实现代码，Canon 路由到对行为具有权威性的代码。

**[实测]** 为什么载体是 Git 而不是 Issue，四条各自独立成立：**版本固定**——Git 能引用某个 commit 的 blob，内容永久固定；Issue body 可被编辑。本项目的 `spec-checkpoint.py` 对 body 取哈希并发布 comment permalink，**这个脚本存在本身就是证据**：它在给 Issue 补 Git 天然就有的能力。**主题组织**——Git 有路径层级可 grep，Issue 是扁平序列只能靠搜索，而检索排序不拥有裁决权。**生命周期冲突**——Issue 的生命周期是任务的，事实的生命周期是事实有效期的；一个契约若定义在已关闭的 Issue 里，要么读关闭的 Issue（`state` 失去意义），要么事实丢失。**离线可读**——Git 内容在 clone 里，Issue 需要网络与 token。

**被否决：** 不设独立层，把方向与契约分散进 Issue body 和 Milestone description。**否决理由：** 那在小项目上成立，项目变大后 Issue body 装不下架构决策、跨模块契约与被否决方案——而这些恰好最不可推导、最需要权威位置。

**保留的判断：** 实现行为与预期行为各有权威，因为它们回答不同的问题；不一致是待处理差异，不能用"代码优先"或"文档优先"自动消除；已经写出的代码不能反过来重新定义目标。

### 8. `canon-map.yaml` 暂不加适用范围维度

目标设计曾承诺路由的底层关系是"适用范围 → 权威来源"，可按路径或领域查询。实现目前只有 `id → target`。

**[实测]** 现在 8 个条目全是项目级的，加 scope 字段所有条目的值都相同、没有信息量；而代价是改两处窄解析器（`repo-context.py` 用正则解析，其注释明说"not general YAML"，模板里另有一份副本）、安装器的生成逻辑与测试 fixture。

**触发条件：** 出现第一个非项目级 canonical target 时加。本项目是方法库，没有业务模块，那一刻还没到。

### 9. `unknown` 区分未决与未登记

**[故障]** 一个实例读到某依赖方在仓库快照里"未登记清楚"，把"资料没登记全"解读成"业务上尚未决定"，于是自行拼出了不在任务范围内的比较调研，制造了不该存在的待决事项。它自己的复盘是"浪费了一轮调研"。

原有规则只覆盖"检索无结果不等于没有约束"，没覆盖"记录里写着 unknown"。现在事实层的 `unknown` 必须区分：**未决**需要一个决定；**未登记**需要你去找到那个决定，而不是做出它。

### 10. 旧机制文档直接删除，不留 stub

一度考虑把 11 份旧文档改成指向 `mechanics.md` 的 stub，理由是 `docs/evidence/` 里的历史证据引用了那些路径。

**[实测]** 那些引用是 JSON 数据里的路径字符串（形如 `"docs/corp/spec-authoring.md"`），不是 markdown 链接：固定 commit URL 0 条、相对路径链接 0 条。它们记录的是"在某个 commit 时读了这个路径的文件"，而那个 commit 里文件确实存在。删除当前版本的文件不会让任何历史证据悬空。

**附带收益：** 本体 `docs/corp/` 与分发模板 `skills/cybercorp/assets/corp/docs/corp/` 的逐字节一致得以保持（模板里放 stub 会让每个新项目一开机就带着指向自己没有的历史的死文件）。

### 11. 仓库改为常规开源结构，许可证 MIT

**[推导]** 判断标准换成：成熟开源项目的常规做法是行业长期沉淀的"什么有用"的判断，把它当默认 baseline，只为真正的例外举证。据此新增 LICENSE、NOTICE、CHANGELOG、CONTRIBUTING、`docs/verification-status.md`；`docs/plan.md`（内容混了已完成／进行中／验证状态三个时态）、`docs/corp/preparation.md`（内容就是贡献指引，位置错在机制层目录）、`docs/source-notes.md`（出处声明，常规位置是 NOTICE）的内容迁入上述位置后删除。

**保留的例外，已在 README 说明：** 本仓库用自己的方法开发自己，因此 `.agents/` 与 `docs/corp/` 是它自身的安装结果，与 `skills/cybercorp/assets/corp/` 这个分发源并存。

**MIT 而非 Apache-2.0：** Apache-2.0 的 NOTICE 机制（第 4(d) 条要求下游保留 NOTICE 内容）曾是选它的唯一理由，但那个目的用"把出处声明写进 README"就能达成，且更可靠——README 一定会被读。MIT 的优势是实在的：最短、采纳阻力最小、与 GPLv2 兼容。

### 12. 吸收规格缩短，保留验收场景

`docs/specs/delivery-communication-verification.md` 从 214 行降到 95 行。

**[实测]** 它的规则正文与 `mechanics.md` 逐条重复（"审查者不能是实现者""完成 = PR 存在且检查通过""沉默不产生授权"等逐句对应），且两者已在各自演化——`mechanics.md` 用 S1–S8 编号体系，那份规格完全没有引用这套编号。维护双份等价文本会持续产生"改一处不改另一处"的漂移。

**保留：** 问题陈述、表达层要求（`mechanics.md` 只管机制不管表达）、以及 12 个独立消费验收场景——那是可执行的验收表，`mechanics.md` 没有。同时给每个场景补了一列，标注它验证哪个子问题。

## 这次判断是怎么得出的

**[推导]** 值得记录，因为它决定了结论的可信程度。

机制层重写前先做了一次 clean-room 推导：由一个**没有读过本仓库任何材料**的实例，只拿到需求陈述（两个硬前提、第一性、已知失败模式、约束），并被禁止使用既有术语（Canon、Corp、Corpo、CorpMech、Plan／Work／Review 作角色名、Issue as Spec、Spec Wave、claim、canon-map），要求它自己命名。禁用术语的目的是检验收敛：如果重新推导后仍然需要等价物，那是强证据；如果切分不同，那是发现。

它独立推出八个子问题，**在原有实现里全部有对应机制，没有一个是漏的**，且多数原有机制更强。由此得到本次重构的性质判断：**方向是对的，结构有问题。** 因此没有做整体重建——原有机制的实质内容是真实故障的解，无法从第一性推出，只能靠实际撞上，那是本项目最有价值的资产。

约束条件：执行这次重写的实例在此判断之前已经读过实现，因此不具备做 clean-room pass 的资格（"读过旧实现之后再声称第一性"是该方法的第一条反模式）。分工由此确定：clean-room 推导由未污染的实例做，salvage（判断旧实现里哪些值得保留）由读过实现的实例做。

## 未决

- ~~**那个 pilot 的权利归属。**~~ **已解决，见[决策记录 0003](0003-remove-inherited-code.md)。** 2026-09-12 的核查确认那个 "earlier maintainer-owned pilot" 是一个具体的外部仓库、其内容与公司产研方案相关、且 `spec-checkpoint.py` 与来源字节完全相同；权属未被任何证据确立。处置是把继承的代码全部替换为 clean-room 原创实现并删除 `NOTICE`，而不是等待权属确认。
- **分发形态。** 本项目目前的使用方式是 clone 仓库、手工运行安装脚本，那是"人可运行的工具"，不是"可被 Agent 调用的能力"。它有 launcher（怎么拉起一个 agent 实例并让它进入某个 Corp），但没有 adapter（怎么让任意 agent 具备创建 Corp 的能力）。
- **验证的两层拆分。** 现有合成消费验证把"环境是否可用"（确定性，可 CI 化，且能捕获 bundle 与当前代码的兼容性腐烂）和"实例是否理解并做出有价值判断"（非确定性，不可 CI 化）混在一起做，导致失败时归因不确定。
- **`docs/evidence/` 的长期归宿。** 那 1MB 按开源惯例属于 CI artifacts 的范畴，但本项目的验证不是 CI 跑的，所以平台上没有记录，只能自存。CI 拆分建立后，新验证走 artifact，这批存量作为"CI 之前的历史"处置。

## 本次未验证

**新机制没有被任何真实 Corpo 消费过。** 已经过的是：123 项自动化测试、本地结构检查、本体与分发模板的逐字节一致性核对。没有过的是：一个只拿到新入口的实例能否据此完成一次真实交付、需要 Owner 介入几次。在取得这个证据之前，本文所有关于"注意力预算下降"的判断都是设计意图，不是实测结果。
