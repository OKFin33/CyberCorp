# 0013 · 声明前提，并让「不可取」成为机器可读的

- 日期：2026-09-13
- 状态：已采纳
- 影响面：`README.md`、`skills/cybercorp/SKILL.md`、`docs/corp/README.md`、`docs/corp/mechanics.md`、`.agents/corp/repo-context.py`、`.agents/corp/check.py`、`docs/verification-status.md`、分发模板

## 来源：两次零上下文外部审查

两个没有本产品开发上下文的实例分别审了发版候选，任务只给仓库路径与两个问题（它想达成什么、达成了吗；一个没有开发上下文的 agent 能否按它的意图使用它）。**不告知设计意图是有意的**——若产品无法自我说明，那本身是第一个发现。

## 第一次审查：最朴素的起点直接不可执行

[故障] 审查者装了一个新项目并扮演接手者，卡在第二步:入口第一句要求跑 `repo-context.py`，而它在无 remote 的新项目上以 `exit 2` 报错终止。随后它去找入口指引的救援文档，发现 `establish.md` **只存在于源仓库，不在生成结果里**。

它从进入到能开工读了 11 份文档，**未到达"知道该做什么"**。

它的诊断准确:这精确复现了本产品 `verification-status.md`「无证据」栏里那一条——不知创建历史的真实接续——而**产品已预判此缺口，未意识到它有多硬**：不是证据不足，是这条路径上直接不可执行。

## 决策一：声明前提，而不是让它在前提不满足时也能工作

Owner 的判断:预期功能本就要求目标是**已建立的 GitHub 托管仓库**。这不是待实现的功能，是边界。

理由成立且比偏好更硬:**机制的每一个原生载体都在 GitHub 上**——Issue 持有工作单元、PR 与 checks 持有完成证据、Milestone 持有阶段、`assignee` 与评论持有占用。没有托管仓库不是降级可用，是这些载体全部不存在。

**声明前提不等于承认缺陷**，如同声明需要 Python 3.9+。此前的问题是它没声明:一个陌生 agent 拿到的是 traceback。

## 决策二：前提说明只在命中时出现

Owner 的要求:正常工作的 Corpo 与明确在建仓的 Agent 都不需要看到这类内容，也不需要去找;只有撞上去的才需要知道为什么并如实报告。

因此:

- **前提声明**放在 `README.md` 与创建包的 `SKILL.md`——读它们的是准备使用产品的人。[实测] `AGENTS.md` 与 `docs/corp/README.md` 中前提相关内容命中 0 处，正常路径上完全不可见。
- **前提不满足时的结论**放在工具的错误输出里，只在跑它且失败时出现，并给两个角色各一句可执行动作:工作者停下并报告这不是 Corp;建立者先创建托管仓库与远端。
- `check.py` 对未完成建立的提示**不再指向 `establish.md`**——那个文件不在生成结果里。改为"发现此情况的工作者应停下并报告，建立 Corp 需要 Owner 在场，不是这个仓库该领的活"。**要求执行者去找一份它没有的文件不是可执行的指引。**

## 决策三：区分「不是 Corp」与「暂时连不上」

Owner 追问后发现的漏项:有 remote 但连不上（凭据、网络、权限）此前输出 `gh: Bad credentials (HTTP 401)`，**执行者从那句话里既读不出该停也读不出该继续**，最可能错误地得出"这不是 Corp"然后放弃。

两者处置相反，因此新增 `Unreachable` 类别，其输出附带处置说明:这不能证明该仓库不是 Corp，只证明这次读取失败;暂停依赖它的决定，无关工作继续。后半句落实的是机制早有的规则。

**混淆的代价不对称**:把连不上当成不是 Corp 会让正常项目被判死;反过来会让执行者在空壳仓库里反复重试。

## 第二次审查：主场景通了，但暴露判定条件不完整

改后复审，两条路径都走。**路径 B（进入已建立的 Corp）读 1 份文件约 4200 字符加两次观察，共约 1.3 万字符即判断出结论**——对比第一次的 11 份文档且未到达。审查者明确划出额外阅读:为评估机制质量而读的 `mechanics.md` 前 150 行"不是走到该做什么所必需"。

它在真实数据上撞到了入口自己提醒的陷阱并被救下:Issue #7 表面 open、无 assignee、无标签，符合"可取"一档，而读完评论发现工作已交付、在等授权。

**但它是靠读完全部评论才发现的，那不是机制给的。**

## 决策四：两个信号，缺一不可

[实测] 新增的 `open_candidates` 字段（每个 Issue 附带引用它的未合并 PR，零额外 API 调用，因为那次读取已返回 PR body）对 `#7` 返回 `[]`——**PR #13 已关闭，不在 open 列表中**。

所以两个信号各覆盖一半，都需要:

| 信号 | 覆盖 | 不依赖 |
|---|---|---|
| `open_candidates` | 候选正在进行 | 任何人记得做动作 |
| Owner-decision 标签 | 候选已关闭或合并而 Issue 仍开 | —— |

随之写入的判据:**依赖执行者记得做一个额外动作的规则，总会在某处未被执行**——四个实例交付后都没标那个标签，而规则当天才写下。候选信号正是为那种情况准备的。

入口另加兜底:两个信号都没有而 Issue 自己的评论说已交付时，**信评论并补上标签**——那意味着正好撞上可读信号未被维护的那次。

`mentions_issues` 有意命名为"提及"而非"链接"：PR body 里的 `#N` 不构成原生关联，该字段的含义是"取那个 Issue 前先核实这个候选"，不是"这个候选关闭那个 Issue"。

## 不修的一项

审查者还发现 PR #17 与 PR #13 范围重叠。**那属于规划未把单元分离好**（单元应按独立可交付划边界），而本例的重叠是同一执行者连续提交多批机制层改动造成的工作方式问题，不是选工时该由机制解决的事。

## 一处不够精确，记录而不掩盖

`#7` 被标为需要 Owner 决定，而它实际等的是一次独立消费验证——**那是一个事件，不是一个决定**。归入该类的理由是该事件的时机由 Owner 安排。若将来"等外部条件"的事项增多，这一类会变得混杂，那时才值得区分;现在只有一例，为它造新概念不划算。

## 顺带修正

`docs/verification-status.md` 中"123 项根 unittest"过期，实测 150 项。审查者指出它属文档未同步，非造假。
