# 持续交付、Owner 沟通与验证反馈

状态：吸收规格。适用于 `skills/cybercorp/` 的创建方法、生成内容及其验收；实现与验证状态由[变更记录](../../CHANGELOG.md)与[验证状态](../verification-status.md)持有，目标项目的有效执行规则仍须从自身约定核对，不能从本规格推定已采纳。

产品目标见 [product.md](../product.md)，完成记录由[变更记录](../../CHANGELOG.md)持有，进行中的工作由原生 Issue 与 Milestone 持有。本规格提供完整的通用要求，实施与验收不依赖试点仓库或私人对话。

> **2026-09-12 收敛。** 本规格原有的机制规则正文（阶段驱动选工、可审候选与交付、双向沟通闭环、验证与失败接续）已按第三节允许的合并方式收敛到 [`docs/corp/mechanics.md`](../corp/mechanics.md)，那里是规则的唯一定义处。本规格保留三部分：本节的问题陈述、第二节的表达层要求（mechanics 只管机制不管表达）、以及第四节的验收场景清单。**规则以 mechanics.md 为准；本规格不再重述规则。**

## 要解决的问题

可替换的 Corpo 需要持续把已接受目标变为交付。只有选工、认领、审查和恢复纪律时，执行者仍可能把普通工程选择交回 Owner，反复寻找审查工作，或在一个阶段结束后失去后续入口。Owner 也需要看懂实际变化、给出纠正或决定，并让后继实例继续消费这些答复。

三项能力接到同一工作循环中：阶段缺口决定下一动作，双向沟通补充人的判断，适用于实际版本的验证反馈推动修正。安装工具继续负责确定性落文件；目标判断、表达选择、项目适配与交付判断由 Agent 承担。

| 使用者 | 需要完成的事 | 可观察的结果 |
|---|---|---|
| 创建 Agent | 为新项目建立方法，或向已有 Corp 补齐能力 | 后继者仅凭项目入口与原生工作即可发现、消费相关方法 |
| 工作 Corpo | 找到并完成当前阶段的真实剩余结果 | 有适用工作时推进实现；缺供给时形成可执行工作；审查后继续修正 |
| Owner | 理解变化、提出反馈、作必要决定 | 能指出本次结果、证据边界和所需回应；答复进入共享依据 |
| 接续 Corpo | 从阶段记录、答复与失败证据恢复 | 不依赖原实例记忆，不重做已交付成果，能继续实际剩余工作 |

## 一、机制规则

见 [`docs/corp/mechanics.md`](../corp/mechanics.md)。规则按八个子问题组织，每条注明它服务哪个子问题、消除执行者必须猜测的哪一处。入口、统领规则、开工必读与场景路由在 [`docs/corp/README.md`](../corp/README.md)。

## 二、Owner 沟通卡的写作要求

mechanics 规定沟通的机制（答复归属、三态区分、授权边界），不规定表达。表达由项目自有的、可替换的卡持有。首版默认落点建议为 `docs/corp/owner-communication.md`，由入口的场景路由直接链接；路径已有 owner 时复用实际位置。

以下是写作维度，不是必填 schema：

- 读者及其当前判断任务、已知的技术背景。
- 语言、语气、详略与解释层级。
- 如何说明结果、变化、证据边界、建议与所需回应。
- 什么时候使用案例、前后对比、图示、演示或技术详情。

沟通前读取当前卡；准备、实现、阶段审查、失败修正和交付共享同一入口。卡与当次 Owner 明确要求冲突时按有效指示处理，必要的长期修正回写卡。卡不持有产品验收、权限或工作状态。

面向非技术 Owner 的示例要求：

> 使用 Owner 熟悉的语言，结论先行、简洁表达。通过使用场景与实际变化说明结果，不靠展示具体代码解释工作。讲清验证证明了什么、还不能保证什么，以及需要 Owner 判断什么。技术证据保留可追溯入口，按需要展开。

同一机制也应支持技术型 Owner 的卡，例如优先解释行为变化、关键取舍和必要的代码／协议差异，再链接精确验证。替换卡只改变表达；两种卡都必须保留重要失败、证据边界与待决事实。

截图、案例或流程图由解释需要决定。示意与运行证据分清；旧行为未知时不虚构前后对比。纯工程改动说明解除了什么障碍，不包装成未实现的用户功能。不统一规定所有 Corp 使用中文、隐藏代码、固定栏目或汇报频率。

## 三、交付形态与旧项目采纳

运行期方法由包内 assets 持有，创建适配说明由创建 skill 持有；实现者可以合并文件，但须保持唯一内容来源与按需读取。**机制层已按这一条收敛**——2026-09-12 起分发的机制是入口加 mechanics 两份，加项目自有的沟通卡；此前的十一份场景文档已并入其中，当前权威落点见 [`docs/corp/canon-map.yaml`](../corp/canon-map.yaml)。

普通 work 只需知道路由和关键触发；阶段、沟通与失败处理在发生时读取。比较更新前后同一场景的冷读成本，减少重复正文；不能通过遗漏必需历史或规则来缩短上下文。

新建项目获得中性的沟通卡起点，创建 Agent 在交接前消费已知偏好并完成适配。已有项目优先复用自己的卡、渠道和检查；不用新增安装输入 schema 才能开始首版。确有必要的安装器变化须由实际生成／碰撞行为驱动。

旧项目经自身变更流程逐项采纳方法与新增链接目标，保留自有编辑、有效 Spec pin、明确审查承诺和初始安装溯源。重装继续拒绝覆盖；文件进入目标仓库、成为有效约定、被运行实例消费分别验证。

不扩展启动器、常驻调度、人员系统或平行状态库。其他任务平台／通知适配器与智能选测，仅在真实接入或耗时需求出现时另行考虑。

## 四、验收

### 可执行与包装检查

- 从独立复制的创建包生成新项目；所有新增路由和卡目标可读取，项目不依赖包外 skill／个人路径。现有项目的卡、检查和自有编辑经重装仍保留。
- 核验普通 work、阶段 review、Owner 沟通与失败修正各自的实际阅读路径；旧的逐 PR 强制触发被完整替换，既有明确审查要求可继续执行。
- 对真正新增的检查逻辑验证错误传播、失效链接／基线与复现输出；Git 行为用真实临时仓库。CI 组合核对实际执行命令和实际 checkout，配置模型测试不能代替托管运行。
- 完成仓库要求的测试与相关包检查。新增业务测试接线用可观察的失败与修正验证，不以自然语言关键词命中作为行为验收。

### 独立消费场景

使用合成项目与虚构身份，先给消费者目标仓库、原始场景和实际环境，冻结其动作与产物，再对照判据。下表为验收者判据，不作为消费者的期待答案。仅检查本轮新增或改变的能力；不重复已有全套协议试验。

「子问题」列指向 [`mechanics.md`](../corp/mechanics.md) 中该场景所验证的规则所属节。

| 场景 | 子问题 | 判据与需要的证据 |
|---|---|---|
| 项目有目标与材料，缺交付安排或明确开发起点 | S1 S4 S6 | 准备者形成覆盖完整范围的路线、近期重点、开发边界与首批工作；不知其过程的后继者实际完成有贡献的结果 |
| 已接受目标未完成，队列为空或已有工作未覆盖必要结果 | S4 | 有界 plan 补齐必要工作并实际推进；已有承接被复用，普通排序不反复交 Owner |
| 基础设施是必要前置或最终交付，部分后续条件已满足 | S4 S6 | 尊重真实前置和他人承接，允许已满足条件的工作并行，不套用固定领域顺序或阶段关闭门槛 |
| 普通 PR 无 review，仍有可实现任务 | S3 | 继续适用 work；保留另一个带明确审查承诺事项的要求 |
| 多实例进入同一可审阶段 | S2 S3 | 深入前发现和声明，完整 review 有界收敛，晚到者提供增量或转做工作；保留实际时间与动作，不能据顺序回放宣称并发已验证 |
| 多个局部 PR 通过但无可用整体 | S3 | 不宣称阶段可验收，先补集成候选／必要输入；其他独立工作继续 |
| 整体审查发现阻断与可选改进 | S3 | 阻断关联实际修正和独立复验，可选改进不扩张本期；交付核对最终版本和下一入口 |
| 相同事实、两张不同 Owner 卡 | 本规格第二节 | 非技术版与技术版的表达确实不同；结果、失败、证据和所需决定保持一致；替换卡不需改通用协议 |
| 记录请求后原实例离席，Owner 随后答复 | S8 | 请求、送达与回应状态准确；后继者取得答复并完成必要 Spec／Canon 采纳，再继续实际工作；不把已读或超时当授权 |
| CI 在旧版本通过、当前基线或 head 改变 | S3 | 检查实际测试对象与影响，只使用仍适用的证据，必要时补检 |
| CI 失败已有修复承接，另有独立工作 | S3 S7 | 失败可按仓内命令定位、复现并接续，不抢重复修复、不冻结全项目 |
| 增加行为但只有旧骨架绿灯 | S3 | 补行为与边界测试并接入实际检查，完成修正；没有所需环境时保留未验证范围 |

沟通卡消费试验只证明方法能够改变表达。Owner 是否看懂，需由实际 Owner 对具体 brief 的反馈确认；通知接通、跨实例接续、真实并发与阶段交付也各自需要对应环境中的直接证据。

### 成功判断与剩余不确定性

功能验收看上述必需行为是否成立，记录实际结果、所需人工干预、重复劳动、隐藏输入和阅读成本，不凭空设定效率提升比例。主要待验证假设是：以阶段缺口选工能改善持续交付，同时没有把必要纠错拖到过大的阶段末尾；阶段尺度应通过真实项目结果校准。

文件拆合、最小检查实现与合成场景规模由实现者按上述要求决定；目标项目具体阶段、Owner 卡和 CI 工具链在创建／采纳时适配。缺少独立实例或托管运行权限时，先完成可做工作，留下具体未验证项，不将未执行写成通过。
