# 持续交付、Owner 沟通与验证反馈

状态：吸收规格。适用于 `skills/cybercorp/` 的创建方法、生成内容及其验收；实现与验证状态由[计划](../plan.md)持有，目标项目的有效执行规则仍须从自身约定核对，不能从本规格推定已采纳。

产品目标见 [product.md](../product.md)，实施顺序与完成记录由 [plan.md](../plan.md) 持有。本规格提供完整的通用要求，实施与验收不依赖试点仓库或私人对话。

## 要解决的问题

可替换的 Corpo 需要持续把已接受目标变为交付。只有选工、认领、审查和恢复纪律时，执行者仍可能把普通工程选择交回 Owner，反复寻找审查工作，或在一个阶段结束后失去后续入口。Owner 也需要看懂实际变化、给出纠正或决定，并让后继实例继续消费这些答复。

本轮把三项能力接到同一工作循环中：阶段缺口决定下一动作，双向沟通补充人的判断，适用于实际版本的验证反馈推动修正。安装工具继续负责确定性落文件；目标判断、表达选择、项目适配与交付判断由 Agent 承担。

| 使用者 | 需要完成的事 | 可观察的结果 |
|---|---|---|
| 创建 Agent | 为新项目建立方法，或向已有 Corp 补齐能力 | 后继者仅凭项目入口与原生工作即可发现、消费相关方法 |
| 工作 Corpo | 找到并完成当前阶段的真实剩余结果 | 有适用工作时推进实现；缺供给时形成可执行工作；审查后继续修正 |
| Owner | 理解变化、提出反馈、作必要决定 | 能指出本次结果、证据边界和所需回应；答复进入共享依据 |
| 接续 Corpo | 从阶段记录、答复与失败证据恢复 | 不依赖原实例记忆，不重做已交付成果，能继续实际剩余工作 |

## 一、由阶段结果驱动工作

### 阶段约定与规划

Corpo 的首要任务是在已接受的目标和授权内完成项目。plan、work、review 是当前工作动作；实例可以转换动作，独立性按其对具体成果的实际参与判断。

- Phase 2 从已接受目标、使用／验收场景与现有成果推导主要交付，形成或复用覆盖完整范围的粗粒度阶段路线；按价值、已约定优先级和实际依赖安排近期重点。远期只明确结果与主要前提，近期细化到可执行工作；开发中按实际变化校准受影响部分。
- GitHub Milestone 持有本阶段结果、范围、必要前提、验收场景与证据等级、后续方向及事实来源。产品承诺继续由其既有 Canon 持有。阶段数量、领域、时长和交付形态由项目决定。
- `current-delivery-focus` 发现当前阶段；后续阶段通过原生对象链接发现。实现工作归属实际 Milestone，按需要使用原生依赖。导航不复制动态路线或任务状态。
- plan 沿现有 `work:coordination` 集合先发现、声明和收敛，再深入规划。复用仍开放且范围适用的事项；新一轮有真实结果才创建有界事项，不重新激活已完成历史。
- 既定目标内的普通排序、任务展开、可逆内部方案和修法由 Corpo 判断。改变产品承诺、验收、已约定优先级或权限时，取得相应 Owner 决定。

全项目准备与阶段开发分别验收。现有 Phase 1／Phase 2 描述的是 Corp 建立与准备能力，不要求目标项目采用相同阶段命名，也不要求所有未来设计先细化完毕。

Phase 2 同时将近期结果映射到足够开工的开发骨架：模块职责、必要接口与数据归属、集成边界、维护位置及实际构建／检查入口。复用已有结构，按需补齐并采纳 Canon，普通设计由 Corpo 解决。首批工作具备结果、可得输入、真实依赖和直接检查；缺少工程起点时明确放入近期前置工作，不伪装成已可运行。非代码项目使用相应的成果结构、生产工具和检查入口。

准备交接的证据是后继者仅凭共享入口就能理解整体范围与路线，说明近期先做什么、为什么、在哪里实现、依赖什么及怎样检查，并开始推进。文档齐全不单独构成完成；材料补齐与设计可往返，不添加固定规划角色或审批阶段。

### 下一动作

| 当前缺口 | 下一动作与出口 |
|---|---|
| 已有工作推进近期必要结果或前置 | work：核对约定和执行权，完成结果与自查 |
| 交付缺必要承接或依赖衔接，即使队列非空 | plan：补齐输入可得、结果明确、能被接手的工作并推进 |
| 整体候选可验收，缺独立阶段判断 | review：固定对象，承接一轮有界整体审查 |
| 审查发现验收阻断 | work：修正并复验；确需跨事项安排才再 plan |
| 最终结果和证据成立 | plan：核对交付、共享记录与下一阶段入口，完成收口 |
| 缺少必要输入、决定或权限 | 明确影响与恢复条件，继续独立工作；无可推进工作时交接退出 |

普通 PR 尚无独立审查不自动产生 review 工作。显式窄任务保留原范围，自主项目工作则对照当前阶段继续推进；局部等待不要求实例停下所有独立工作，也不要求它永久在线。

基础设施可以是主要交付或必要前置，按实际目标判断。后续工作满足其能力与输入前提即可推进，不以先前 Milestone 全部关闭作为额外依赖。已有安排充分时直接执行；普通选工不增加报告或全项目重规划步骤。

### 可审候选、修正与交付

阶段 review 的入口是可执行验收的整体：主要承诺已有实现；有一个可取得、可重建的固定集成候选；必要环境、输入和约定场景可用；结果与证据、已知缺陷及未验证范围可对照。候选可以带已知缺陷，但不能缺使主要验收无法开展的整条能力或环境。

在本轮共享事项中固定候选版本、范围、阶段约定及必要 Canon／Spec 输入、环境和已有证据。可变 Milestone 说明用该时点快照、来源与时间固定为审查证据；不另行维护一份阶段事实。

阶段整体 review 复用现有统筹入口及 claim 收敛，避免重复昂贵检查。明确请求的单 PR review 在原 PR 上先用普通评论声明实例、固定对象、范围和有效期限，重读已有承接后再深入；完成、退出或转做实现时更新承接情况。无需人为新建子 Issue，也不把声明当作原子锁。发现重复时保留增量，退出重复部分。

审查由未参与被判断实现的实例承担。审查期间不修改该对象；结束并释放后可以正常承接修正，修正的独立复验交给未参与者。自查属于 work，不因更换名字或分多次思考变成独立 review。

审查发现按实际后果处理：

- **验收阻断**：给出违反的约定、场景、后果与复验条件，纳入本阶段修正。
- **非阻断改进**：作为后续候选，不自动扩展本期范围或为每条建议开票。
- **真实决定**：涉及改变目标、验收或权限时，通过 Owner 沟通取得决定。

小修留在原事项，确有独立交接或并行价值才拆分。每个阻断发现关联实际修改、精确新版本与复验；检查变化的影响和必要阶段链路，不机械重审所有未变内容。新出现的真实验收失败仍须处理，优化建议不能使阶段无限延长。

PR 发现与结论使用原生 Review／行内评论；权限不支持时在该 PR 记录结论与限制。阶段整体结论留在本轮 Issue，链接相关 PR、Review、CI。沟通摘要引用这些证据，不另造审查台账或承载结论的空 PR。

正式交付要求：必交结果达到原证据等级，阻断项已处置并有有效复验；成果与修正经过必要授权并实际集成，证据适用于最终交付版本；必要 Canon 和消费者同步；非阻断余项有去向；下一阶段入口可发现，或项目已明确完成。不得通过迁出必交工作制造完成。

需要切换当前焦点时，按正常变更与 merge 授权先使新入口可用，再关闭旧阶段。外部条件缺失时如实标明下一阶段尚未就绪；项目终期保留可发现的完成记录，必要时使用显式事项读取，不伪造活跃阶段。客观收口不额外增加例行审批，部署、数据变更与真实外部调用仍按各自授权。

### 替换逐 PR 默认审查要求

普通变更由 work 完成自查、必要测试、结果与风险说明。独立审查由阶段候选、明确请求或已接受约定触发；高影响变更在 merge 沟通时说明具体影响与已有证据，由 Owner 结合该次合入决定是否要求额外审查。

实现时同时更新 development-loop、work-corp、review-corp 和 claim-protocol 中的默认触发，避免新旧规则并存。既有明确审查承诺持续有效；本轮机制变更自身按开工时的有效规则交付，不能提前用新规则豁免。每次 merge 的具体 PR／head／checks／方式及单次授权保持有效。

## 二、双向沟通与可插拔沟通卡

### 能力分工

| 部分 | 持有的内容 | 项目如何适配 |
|---|---|---|
| 通用沟通机制 | 沟通目的、记录与送达、答复回流、等待和接续 | 随 Corp 方法安装；引用项目的实际渠道与沟通卡 |
| 实际沟通渠道 | 当前会话、关联 PR／Issue、已有且获准的通知渠道 | 由项目／运行环境持有接入、身份和权限，不把凭据放入卡 |
| Owner 沟通卡 | 面向谁、帮助其判断什么、语言、详略、解释与展示方式 | 项目自有 Markdown，可修改、替换或引用已有同类文档 |
| PR 等表达模板 | 引导作者按当前卡形成一次具体沟通 | 保留短提示和链接；不复制卡正文成为第二份偏好配置 |

“可插拔”的最小实现是一个可发现的文档引用和可替换内容。无需卡注册表、解析器、插件服务或新增状态模型。创建 Agent 根据已有 Owner 指示和项目材料形成卡；已有同类文档时直接引用。缺少偏好时使用中性、清楚、事实完整的起点，不让填写一套个人画像成为开工条件。

### 卡的内容与消费

首版默认落点建议为 `docs/corp/owner-communication.md`，由通用沟通方法直接链接。路径已有 owner 时复用实际位置。以下是写作维度，不是必填 schema：

- 读者及其当前判断任务、已知的技术背景。
- 语言、语气、详略与解释层级。
- 如何说明结果、变化、证据边界、建议与所需回应。
- 什么时候使用案例、前后对比、图示、演示或技术详情。

沟通前读取当前卡；准备、实现、阶段审查、失败修正和交付共享同一入口。卡与当次 Owner 明确要求冲突时按有效指示处理，必要的长期修正回写卡。卡不持有产品验收、权限或工作状态。

面向非技术 Owner 的示例要求：

> 使用 Owner 熟悉的语言，结论先行、简洁表达。通过使用场景与实际变化说明结果，不靠展示具体代码解释工作。讲清验证证明了什么、还不能保证什么，以及需要 Owner 判断什么。技术证据保留可追溯入口，按需要展开。

同一机制也应支持技术型 Owner 的卡，例如优先解释行为变化、关键取舍和必要的代码／协议差异，再链接精确验证。替换卡只改变表达；两种卡都必须保留重要失败、证据边界与待决事实。

截图、案例或流程图由解释需要决定。示意与运行证据分清；旧行为未知时不虚构前后对比。纯工程改动说明解除了什么障碍，不包装成未实现的用户功能。不统一规定所有 Corp 使用中文、隐藏代码、固定栏目或汇报频率。

### 沟通闭环

1. **明确本次目的。** 进展、建议和非阻塞征询可以与已授权工作并行；必要决定或授权说明事实、推荐、影响和需要的回应，只等待受影响范围。
2. **选用已有载体。** 有 PR 的变更用 PR 标题、正文或评论；尚无 PR 时用关联 Issue／当前会话。影响后续工作的内容有共享落点，轻量讨论无需都变成任务。
3. **实际送达。** 当前可交互会话直接沟通；无人值守时使用已配置且获准的渠道。写入记录、发送成功、收到回应分别报告，未配置渠道时留下请求及缺口；不承诺未具备的通知或自动唤醒。
4. **归属与采纳答复。** 保存答复者、来源渠道、时间、适用范围及可用来源。直接来自有决定权 Owner 的可归属答复可以由 Corpo 转录，不要求 Owner 为同一决定例行再次发布；无法核实来源或决定权时只核实受影响决定。按实际变化更新 Spec／Canon 和消费者，记录收到不等于已采纳或已执行。
5. **等待与接续。** 阻塞实施时写 checkpoint、恢复条件并释放 claim。答复到达后，原实例或后继者重新核对决定、当前约定、产物和执行权再继续。没有运行实例时由现有入口再次启动；沉默、已读或超时都不产生授权。

卡约束沟通方式，通用机制持有上述闭环。禁止遗漏失败等事实要求不会因为换卡而消失；卡也不能授予发送、merge 或其他外部动作权限。

## 三、可复现的验证与失败接续

验证应让后继者取得同一对象、执行仓内命令、解释实际结果，并继续修正。首版保留简单的检查组合，项目行为测试随实现增长。

### 通用检查与项目检查

- Corp 检查只覆盖所交付的入口／链接、路由、方法发现和辅助工具的适用结构与可执行契约；不能据这些检查判断自然语言方法已被正确消费。
- 项目检查由实际构建文件、测试、锁文件和文档持有。创建 Agent 复用已有入口，将 Corp 检查接入其适当位置；没有入口且本次确需验证时补最小组合，不引入检查插件框架。
- 新功能或修复的测试须进入实际运行入口。缺少业务测试不能以骨架构建绿灯代替；无适用检查时报告缺口，不能空跑后宣称业务通过。
- 本地与 CI 使用相同的仓内命令和声明输入。环境差异保留证据，不承诺任意机器必然得到相同结果。依赖和工具链可从项目取得，秘密与真实外部接入仍通过项目授权方式提供。

目标项目有 GitHub CI 时按本规格适配；无 CI 的本地创建仍可验证本地结果，CI 缺口按实际交付要求保留。生成器不自动配置账号、Secret、分支保护或外部运行。工作流内容由创建 Agent 结合项目检查形成，不复制某个试点的应用数、技术栈或领域约束。

### 版本和运行证据

适用的 GitHub 工作流覆盖 PR 候选与默认分支实际集成结果，手动入口按需保留。沿实际默认分支配置，不写死 `main`。

同一 PR 的过时运行可以被替换；默认分支连续提交和手动运行各自保留证据，不能因为共享并发组互相取消。运行容量、平台故障或人工取消仍可能使结果缺失。

每项检查能定位实际测试 commit、输入／环境、事件与 attempt、job／step、结果和复现命令。PR 的 head 与平台合成的 checkout commit 分别核对；最终默认分支证据必须对应实际合入版本。基线或候选变化时评估证据适用性，按影响补检。

Git 差量检查打印实际范围，使用有效 PR 基线或 push 的前一版本；初始提交按整树处理。手动／本地默认范围明确可见，允许指定基线复现，必要时包含暂存与未暂存改动。应有而缺失或不可用的基线须失败，不能退为空区间报通过。

### 失败后的工作

从具体失败步骤与版本区分代码／契约错误、环境获取失败、被替代运行及未执行。保留失败证据，在自己的 checkout 按仓内命令复现；修正真实原因，验证新版本及其影响。对已判断的临时平台失败可以有界重跑，不能无限重试或禁用检查制造绿灯。

PR 修正通常留在原工作。共享默认分支失败时先核对当前版本和已有承接，优先恢复受影响基线；只在有独立剩余结果时新建事项。缺少权限或外部输入则保存错误、已做检查、剩余与恢复条件并释放，只暂停相关范围。CI 不自行派工、审查、合并、部署或唤醒实例。

Owner 沟通按当前卡说明失败影响、已修结果与未验证边界，并链接原生运行；不复制动态 CI 状态表。测试通过只证明其实际检查范围。

## 四、交付形态与旧项目采纳

以下路径是实现建议。运行期方法由包内 assets 持有，创建适配说明由创建 skill 持有；实现者可以合并文件，但须保持唯一内容来源与按需读取。

| 内容 | 维护来源／建议落点 | 何时消费 |
|---|---|---|
| 工作目标、动作选择与路由 | 现有 `skills/cybercorp/assets/corp/docs/corp/development-loop.md` 与生成入口 | 开始或恢复工作 |
| 阶段约定、候选、复验与交付 | 新 `skills/cybercorp/assets/corp/docs/corp/milestone-delivery.md`；现有三个 skill 与 coordination 链接 | plan、阶段 review、修正复验、阶段交付 |

| 项目自有表达卡 | 新 `skills/cybercorp/assets/corp/docs/corp/owner-communication.md` 或已有 owner | 沟通方法路由到当前卡 |
| 验证与失败接续 | 新 `skills/cybercorp/assets/corp/docs/corp/verification.md`；必要便携检查工具 | 实施验证、读取 CI、修正或交接 |
| 创建与采纳 | `skills/cybercorp/SKILL.md`、输入说明与安装工具的必要调整 | 新建或补齐项目方法、卡、检查接线 |
| 行为与包装验收 | 现有 `tests/` 加合成消费者场景 | 对实际生成项目验证 |

表内路径相对 CyberCorp 仓库根目录。普通 work 只需知道路由和关键触发；阶段／沟通／失败处理在发生时读取。比较更新前后同一场景的冷读成本，减少重复正文；不能通过遗漏必需历史或规则来缩短上下文。

新建项目获得中性的沟通卡起点，创建 Agent 在交接前消费已知偏好并完成适配。已有项目优先复用自己的卡、渠道和检查；不用新增安装输入 schema 才能开始首版。确有必要的安装器变化须由实际生成／碰撞行为驱动。

旧项目经自身变更流程逐项采纳方法与新增链接目标，保留自有编辑、有效 Spec pin、明确审查承诺和初始安装溯源。重装继续拒绝覆盖；文件进入目标仓库、成为有效约定、被运行实例消费分别验证。

本轮不扩展启动器、常驻调度、人员系统或平行状态库。其他任务平台／通知适配器与智能选测，仅在真实接入或耗时需求出现时另行考虑。

## 五、验收

### 可执行与包装检查

- 从独立复制的创建包生成新项目；所有新增路由和卡目标可读取，项目不依赖包外 skill／个人路径。现有项目的卡、检查和自有编辑经重装仍保留。
- 核验普通 work、阶段 review、Owner 沟通与失败修正各自的实际阅读路径；旧的逐 PR 强制触发被完整替换，既有明确审查要求可继续执行。
- 对真正新增的检查逻辑验证错误传播、失效链接／基线与复现输出；Git 行为用真实临时仓库。CI 组合核对实际执行命令和实际 checkout，配置模型测试不能代替托管运行。
- 完成仓库要求的测试与相关包检查。新增业务测试接线用可观察的失败与修正验证，不以自然语言关键词命中作为行为验收。

### 独立消费场景

使用合成项目与虚构身份，先给消费者目标仓库、原始场景和实际环境，冻结其动作与产物，再对照判据。下表为验收者判据，不作为消费者的期待答案。仅检查本轮新增或改变的能力；不重复已有全套协议试验。

| 场景 | 判据与需要的证据 |
|---|---|
| 项目有目标与材料，缺交付安排或明确开发起点 | 准备者形成覆盖完整范围的路线、近期重点、开发边界与首批工作；不知其过程的后继者实际完成有贡献的结果 |
| 已接受目标未完成，队列为空或已有工作未覆盖必要结果 | 有界 plan 补齐必要工作并实际推进；已有承接被复用，普通排序不反复交 Owner |
| 基础设施是必要前置或最终交付，部分后续条件已满足 | 尊重真实前置和他人承接，允许已满足条件的工作并行，不套用固定领域顺序或阶段关闭门槛 |
| 普通 PR 无 review，仍有可实现任务 | 继续适用 work；保留另一个带明确审查承诺事项的要求 |
| 多实例进入同一可审阶段 | 深入前发现和声明，完整 review 有界收敛，晚到者提供增量或转做工作；保留实际时间与动作，不能据顺序回放宣称并发已验证 |
| 多个局部 PR 通过但无可用整体 | 不宣称阶段可验收，先补集成候选／必要输入；其他独立工作继续 |
| 整体审查发现阻断与可选改进 | 阻断关联实际修正和独立复验，可选改进不扩张本期；交付核对最终版本和下一入口 |
| 相同事实、两张不同 Owner 卡 | 非技术版与技术版的表达确实不同；结果、失败、证据和所需决定保持一致；替换卡不需改通用协议 |
| 记录请求后原实例离席，Owner 随后答复 | 请求、送达与回应状态准确；后继者取得答复并完成必要 Spec／Canon 采纳，再继续实际工作；不把已读或超时当授权 |
| CI 在旧版本通过、当前基线或 head 改变 | 检查实际测试对象与影响，只使用仍适用的证据，必要时补检 |
| CI 失败已有修复承接，另有独立工作 | 失败可按仓内命令定位、复现并接续，不抢重复修复、不冻结全项目 |
| 增加行为但只有旧骨架绿灯 | 补行为与边界测试并接入实际检查，完成修正；没有所需环境时保留未验证范围 |

沟通卡消费试验只证明方法能够改变表达。Owner 是否看懂，需由实际 Owner 对具体 brief 的反馈确认；通知接通、跨实例接续、真实并发与阶段交付也各自需要对应环境中的直接证据。

### 成功判断与剩余不确定性

本轮功能验收看上述必需行为是否成立，记录实际结果、所需人工干预、重复劳动、隐藏输入和阅读成本，不凭空设定效率提升比例。主要待验证假设是：以阶段缺口选工能改善持续交付，同时没有把必要纠错拖到过大的阶段末尾；阶段尺度应通过真实项目结果校准。

没有阻塞规格整理的产品问题。文件拆合、最小检查实现与合成场景规模由实现者按上述要求决定；目标项目具体阶段、Owner 卡和 CI 工具链在创建／采纳时适配。缺少独立实例或托管运行权限时，先完成可做工作，留下具体未验证项，不将未执行写成通过。
