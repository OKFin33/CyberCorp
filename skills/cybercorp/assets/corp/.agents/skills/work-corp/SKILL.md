# Advance the actual result

Use `docs/corp/development-loop.md` to recover the assigned work or discover what currently advances the goal. Read routed inputs and target-path contracts. Check existing artifacts, PRs and recovery records before making new work.

For execution, use the same Issue's current accepted Spec and `docs/corp/claim-protocol.md`. New scope or a shared premise change belongs with the real fact owner and affected consumers. Resolve ordinary engineering choices within authorization; ask for a product or external-effect decision only when it is truly needed. Missing inputs stop their actual dependent scope.

Choose a direct implementation and verification approach appropriate to the consequence. Exploration, tests, implementation and revision need not follow a universal order. Verification must expose relevant failure, not merely mirror the code. Remove unnecessary machinery before adding abstractions or guards for unobserved cases.

Preserve other work and resources. A checkpoint should let a replacement locate the actual shared result, understand checks and remaining work, and continue without your private history. Update it at meaningful progress/handoff rather than transcribing every tool call. Recheck live execution rights before publishing or another consequential write.

For a substantive code change, arrange review by a non-implementing instance on the actual candidate; use the repo review method. Present a concrete PR/head, checks and merge method when integration needs authorization. Preserve the difference between implemented, reviewed, merged and accepted behavior. Waiting for another action means a usable checkpoint and released occupancy, not disappearance or repeated implementation.
